# Autonomous goal completion: Work Sync on Stage 1 Host

**Status:** reviewed design proposal (twelve self-review passes in two batches; independent implementation review and E2E pending), implementation not started. **Parent:** [#982](https://github.com/777genius/agent-teams-ai/pull/982), inspected at `dee94bf14ddbe81143ed2c3c9029a74e66158e1e` (2026-11-27). This is a follow-up, not an amendment to the migration acceptance or authorization to merge/activate it. **Target:** a team with a lead and teammates can finish an explicitly accepted user objective unattended while its supported desktop/Host execution environment is running.

## 1. Decision and scope

Extend the existing Work Sync policy and the Stage 1 Host's current Team/Runtime owners. Do not build a second scheduler, task board, message dispatcher, recovery ledger, workflow engine, external supervisor, or provider framework. The existing [work recovery plan](agent-work-recovery-implementation-plan.md), [D1 admission plan](agent-work-recovery-d1-runtime-admission-plan.md), [control plane](member-work-sync-control-plane-plan.md), and [Stage 1 plan](../plans/provider-migration/stage-1-legacy-host.md) remain relevant. Read the current implementation rather than implementing their historical checklists again.

An explicit **Continue until objective is done** action selects this mode for a specific user request/task and execution run. Off preserves current behavior. Put it in the existing start/delegate UI; a saved preference may remember the choice but opening a team, receiving an ordinary message, or finding an unfinished board must never start autonomous work. Initially support one active objective per execution-team incarnation and authorized run lineage. Unrelated backlog, other projects and ordinary chat remain outside it. No new dashboard or global auto-run switch. Original user permissions and scope still apply.

In scope: lead planning, task pickup, task work, assigned review and changes requested, coordination, final acceptance, normal turn continuation, bounded lack-of-progress recovery, supported temporary error recovery, durable expected waits, recovery/reconciliation after supported restart, stop and visible disposition. Existing task/review workflow stays canonical. Keep ordinary user chat, manual retry, existing schedules, native permissions and non-opted-in teams compatible.

Out of scope: closed-app/OS sleep/power-loss execution, new Orchestrator/Runtime v3 or OpenCode V2, multi-goal orchestration, remote agents, arbitrary integrations/webhooks, autonomous model/provider substitution, auto-approval, auto-merge or deployment without original permission, mandatory model-based verifier, semantic analysis of every transcript, generalized checkpoint engine, rewriting old legacy paths, release/default activation. A running but disconnected/failed Host cannot promise progress until it is recovered. No claim that any model always solves any objective.

Use one small durable Team-owned objective record, not an execution engine. Existing root-task metadata is acceptable only if it proves the same ownership, revision, scope and deletion invariants; otherwise add one record alongside the existing canonical Team state. Suggested fields (reuse names/types already present): `goalId`, original accepted request/message or task-start reference, execution-team incarnation and authorized run lineage, immutable accepted criteria/reference, `revision`, mode, deadline and turn budget, disposition, final result/evidence reference. Store immutable original request by reference when already retained; if the referenced content can expire, retain its bounded immutable criteria/text until goal retirement. No whole-transcript copying.

Use one stable goal association on a task (or existing root-task linkage), captured by the canonical Team owner from the admitted goal-bound input/command, never from a model-supplied arbitrary goal ID. The current [TaskStartCause](../../packages/legacy-agent-host/src/team/TaskStartCause.ts) binds task-start command, message, delivery, input and runtime binding; [TeamCommand](../../packages/legacy-agent-host/src/team/contracts.ts) does not yet expose goal association. Reuse that provenance, extending only missing private receipt/task metadata. Delegated tasks, notifications, review and rework inherit the association from their original authorized cause, not merely because a member is working on this goal. Existing tasks require explicit authorized attachment. Ordinary peer/group/cross-team messages, schedules and foreground user input cannot silently acquire goal authority. Ambiguous association preserves ordinary delivery but does not authorize goal-specific mutation/admission.

Same-team roster changes or reassignment retain goal and budget, invalidate stale recipient bindings and expose remaining work to the lead. Fresh launch, clone, import or another execution-team incarnation cannot implicitly adopt it. A supported Resume binds to a proven successor of the authorized run and reconciles retained debt first. Observe cross-team dependencies via existing authorized state, but do not enroll another team in v1.

The objective's required work is monotonic except for an explicit user-authorized scope revision. A lead may refine the plan or add required in-scope work, but cannot delete/drop a requirement to manufacture success. Deleted tasks leave an unmet obligation until replaced with an explicit linked successor or removed by the user; no permanent duplicate task inventory. Use canonical task history/metadata to preserve that relationship; if the current stores cannot enforce it, the minimal durable association is part of slice C. Avoid a new task store, generic graph or storage migration without a demonstrated invariant.

At intake, bind request and opt-in/limits to the existing authorized user launch, task-start or explicit lead-directed message receipt; first verify the actual path. Same receipt returns the original goal; same ID/different payload conflicts. Persist the goal and first lead-work obligation through existing owner transaction/receipt recovery before acknowledging start; a crash between them leaves recoverable original intent. A simple request can legitimately finish without creating tasks. Preserve the original request by immutable reference: derived criteria are the lead's interpretation, not permission to add merge, deploy, paid operations, wider repository access or other unauthorized effects. Ask about materially ambiguous requirements while continuing independent work. Explicitly selected follow-up may revise the goal under user authority; ordinary chat cannot silently replace/expand it. Additional goals are separate explicit starts after completion/stop, not automatically merged.

## 4. Completion semantics

A turn ending, a model claiming success, an empty per-member agenda or even all board rows reporting completed are not proof of objective completion. Derive the lead's action from the current goal scope:

- Plan/clarify the accepted work and materialize missing required tasks.
- Assign actionable unowned work; resolve broken dependencies, review changes and questions directed to the lead.
- Wait for active delegated work while still doing independent obligations; avoid waking the lead for every child event.
- After required work is finished, run final verification against the current objective criteria and task/review/evidence revisions.
- Persist the final acceptance outcome and publish one final result to the user, using existing message delivery and idempotency.

Acceptance requires the current scope revision, complete canonical read of required work, review/rework, waits, approvals and known unresolved effects. Cancelled/deleted tasks are not successes except explicit user-authorized scope removal or proven in-scope replacement. A missing requirement remains missing even when every board row is complete. Do not equate caught_up or an ordinary chat answer with goal completion. A straightforward task-free request may finish with a verified lead result; no artificial subtasks or mandatory reviews.

### 4.1 Lead obligation projection (not another task list)

Derive at most the following reasons from the canonical goal and board: `plan_required`, `assignment_or_clarification_required`, `review_or_integration_required`, `waiting_for_required_work`, `final_verification_required`. Use a small tagged state/decision, not synthetic tasks for every management event. If the team is waiting only on valid children, do not continually nudge the lead. If no owner can act (missing member, broken/cyclic dependency, unassigned task, rejected plan), make it actionable for the lead once with the specific cause. Do not silently assign a task to the wrong member or grant new permissions. Coalesce board-complete notification and the derived final obligation: the existing canonical notification can wake the lead, but cannot close the objective.

### 4.2 Acceptance is revision-bound

Use one narrow lead-only finalization command: reuse an existing completion/verification path if it can bind goal, criteria, result and revision; otherwise one strict bounded goal-finalize command. Do not overload member_work_sync_report (explicitly not a completion/approval tool). The lead submits criterion outcomes, relevant current evidence references and final result. The Team owner resolves original goal/input and lead authority, validates scope, required task and review/evidence revisions, and rejects failed, skipped, unknown, stale or waiting required outcomes. Reuse existing review/verification; do not bypass human/independent review. For subjective criteria record the accountable lead attestation and limitations, not independent proof. Require Git/CI only when relevant to the accepted request. Verify evidence outside the fence if needed, then short compare-and-commit under the owner; concurrent new required work, rework, scope edit or relevant evidence change invalidates the attempt. No provider/network IO under the fence. No forced extra model turn when complete attestation and result already exist.

Acceptance freezes the revision and closes further goal-driven admissions. Persist the final result and original publication obligation through existing Team/message receipts: distinguish active, accepted/result_pending_delivery, completed (durably available in the user channel) and unknown/held publication. An edit before acceptance invalidates the candidate; after acceptance, a new explicit objective is required. Progress chat stays ordinary. The finalization command produces/references exactly one canonical final publication; recover its stable message ID/payload instead of generating new text on lost acknowledgement. Inbox insertion is not proof of user read. Completion is independent of a mounted renderer; retain original acceptance evidence, unfinished work and held effects.

## 5. Continuation decision

Use one decision per current objective/member/settled input, with current authority, not chat-text heuristics. Reconcile on durable authoritative settlement, task/review/dependency changes, recovery result, due wait and bounded fallback observation. [RuntimeActivityCoordinator.observe](../../packages/legacy-agent-host/src/runtime/RuntimeActivityCoordinator.ts) validates Host incarnation/session and input/operation pairing and persists terminal facts before activity projection. Use the persisted input fact, not log text, a successful projection or an unattributed event. Recover a missed event by level-triggered current-state observation. Debounce/coalesce repeated events; events are triggers, not proof. Reuse the scheduler and current Team/Runtime feed. No new periodic LLM calls while an agent is busy or idle with no actionable work.

| Fresh snapshot | Action |
| --- | --- |
| Exact current runtime busy or approval pending | No new input; retain obligation |
| Settled current input; eligible work, permitted mode and budget | Plan one next turn through existing admission/outbox |
| Review/clarification now actionable | Wake the authorized owner/reviewer/lead through the same policy |
| Waiting on a verified dependency or registered wait | Record wait; no blind continuation |
| Retryable provider failure | Delegate to existing runtime recovery; no concurrent normal continuation |
| Missing identity, stale/partial snapshot, unknown effect | Reconcile; do not start another effect on that binding |
| Stop, explicit pause, permission revoked, limits exhausted | No automatic turn; keep typed reason and unfinished work |
| Nothing eligible, goal still open | Observe next event; classify unresolved responsibility or waiting; do not infer success |
| Goal accepted as complete | Do not schedule further work; deliver final result once |

Implement a small pure decision helper only if the existing Work Sync policy cannot express these distinctions. Keep deterministic rules and narrow ports; no provider-specific logic in the core. Re-read canonical state under the existing admission guard immediately before dispatch, including goal/task revision, member identity, runtime instance, completed input/generation and control revision. A late event from an old generation is diagnostic only. No direct sends or fabricated agent commands. Normal continuation needs an existing supported Host-side system command authority. The inspected [TeamWorkSyncCommands](../../packages/legacy-agent-host/src/work-sync/TeamWorkSyncCommands.ts) and [native message ports](../../packages/legacy-agent-host/src/work-sync/createNativeWorkSyncMessagePorts.ts) require original native input/sender authority; they cannot simply be called with a fabricated MCP proof after a turn has settled. First see whether an existing Team-owned system notification/command can carry the exact authorization. Otherwise add one narrow **private** Host-owned continuation command, behind the existing Team write/receipt and delivery authority, with immutable goal/revision/target/settlement binding. Do not expose a generic system sender to MCP or reuse a previous agent's token. The Runtime owner alone admits and claims its input; use its existing identity, input phases and delivery lookup. The private route must share, not bypass, current Team delivery and Runtime admission/dispatch authorization. No second ledger.

### 5.1 Exact decision and effect boundaries

- Derive the settlement witness from the canonical Runtime record/provider observation for the exact binding, input ID, operation reference and terminal outcome. `admitted`, `claimed`, `consumed`, a Stop hook, UI idle, an empty stream or a log gap are not successful settlement. Non-success terminal outcomes go to the existing recovery/control owner. Do not equate provider turn generation with the Host binding generation unless the adapter proves that mapping.
- One stable decision/effect key per goal revision, target runtime and actionable opportunity: original terminal input/operation plus obligation revision, or canonical new task/wait cause without preceding input. Neither terminal input alone (new tasks can arrive later) nor every read/revision (duplicates) is sufficient. Choose the oldest unconsumed eligible opportunity, coalesce concurrent wake reasons, persist immutable payload and consumed witness. Later obligations remain visible after the current turn. Hold if required proof was pruned, never infer it is new. An existing queued message covers the opportunity only with matching original cause; unrelated foreground/peer input must not suppress goal work permanently or be relabeled.
- Persist one unresolved automatic intent/reservation per member/runtime authority before effects. Revalidate goal/task revision, grant, control, approval, readiness/custody and budget at admission **and** actual durable submit claim. [TeamDeliveryAuthority.deliveryAuthorized](../../packages/legacy-agent-host/src/team/TeamDeliveryAuthority.ts) already verifies receipt, grant, binding, payload, immutable fingerprint and role. Cover any new private metadata variant in every relevant fingerprint/authorization reader; old receipts retain their exact meaning. No arbitrary public system sender or direct provider submit. Preserve existing lock order: short owner-local operations, durable reservation/receipt between owners, guarded Runtime claim; no fence across provider/network awaits or mutually waiting locks. If final claim cannot be fenced against revocation through current owners, automatic execution is not qualified.
- The linearization point for "new work starts" is the existing durable Runtime claim; once accepted Stop/pause closes the corresponding admission fence, no later automatic claim may succeed. A claim ordered before closure can still be in physical handoff; use the original cancel/stop/cleanup contract, report unknown custody honestly, and never pretend it was not sent. Cover both not-yet-admitted and already-admitted unsent inputs. Member Stop must not be bypassed by lead reassignment or a different automatic producer; only authorized user Resume can clear its latch. Team Stop closes all automatic admission for that scope. Do not block user Stop on a model response or external wait.
- Normal continuation, goal-bound task/review/board wake, watchdog and runtime recovery share original cause and admission boundary. Reuse actual producers; do not suppress task state, inbox history, human messages or accepted receipts. Existing member_work_sync_status(forceNudge) is a write-authorized path, not passive readback; it cannot bypass budget/Stop or create a second intent. UI/diagnostic reads never allocate intents. No fallback to generic text or different runtime/member on failed wake.

Read [RuntimeOwner](../../packages/legacy-agent-host/src/runtime/RuntimeOwner.ts), especially `admitDelivery`, `lookupDelivery`, `cancelDelivery`, `dispatchNext`; `consumed` denotes native submit acceptance, not success. Preserve its durable claim and no-replay-on-unknown semantics, current immutable fingerprints, and bounded queue. If the current policy cannot close the actual claim race, slice A remains a qualification blocker for automatic activation, not permission to bypass it.

## 6. Progress, retry and resource budget

Separate productive next turns from failure/no-progress recovery. Keep the existing two-attempt default for no-progress recovery unless evidence justifies a change. Real monotonic progress can permit many productive turns inside the objective's overall resource bounds. Avoid resetting all member budgets because one task moved, clock changed, status was reread, or another agent was active.

Use task-bound evidence from actual task/review transitions, resolved dependencies, accepted artifact/check results or verified operations. Reuse existing task-change/evidence owner and canonical IDs. Relevant new verified substeps can count within a long in_progress interval; read-only research can use a bounded result/checkpoint reference, not a mandatory commit. Repeated evidence, status toggles, same artifact/failed check, empty tasks/comments, model reports, heartbeats, timestamps and delivery acknowledgements alone cannot replenish attempts. Evidence is consumed only for its own current obligation/review cycle; another member's progress cannot reset a stuck episode. Preserve Stop, report lease, unresolved intent and budget across restart/clock change. When instrumentation cannot prove progress, allow only bounded no-progress recovery and then visible attention; no transcript scoring.

Use a simple distinction: ordinary next turn after proven progress (does not debit the lack-of-progress recovery allowance); bounded recovery turn after no verifiable progress (debits it exactly once); due observation of a registered expected wait (counts toward shared run bound, not a fabricated stall). The first planning/pickup turn is ordinary only once per fresh obligation; a model cannot gain fresh allowances by issuing new report tokens or manufacturing equivalent tasks. Prefer actionable dependencies and oldest eligible work within existing member/task priority; do not continually wake the lead while its children run. If one item exhausts its recovery budget, mark that item attention and let independent eligible items progress. A lead may choose a genuinely different in-scope resolution (e.g. correct a dependency or reassign through existing authority), but not cycle owners endlessly to reset the shared budget.

Reuse existing recovery cooldown/rate limits. Proposed initial opt-in preset: 12 elapsed hours and 100 automatic-turn permits shared by the goal's lead and members; explicitly editable by the user. These are provisional design defaults. Count every goal-bound non-human-triggered new native input that can start a turn (continuation, recovery, due wait check, task/review/board/peer wake, runtime retry if it starts a new turn). Otherwise existing notifications bypass the limit. Authenticated direct human input keeps its normal path; automatic descendants count. Inbox persistence, passive observation, controls, cleanup and transport/receipt retries are not new turns. Reserve a permit atomically at the existing Team owner before admission/claim, binding it to the original intent; reservations reduce availability. Consume once at claim; return only on proven no-start, retain on unknown. A producer/tuple without trustworthy origin and claim accounting is not qualified for this mode.

At expiry/exhaustion close new automatic claims, retain required messages/results and existing debt in canonical queued/readback paths; no silent message drops or catch-up flood. Allow previously claimed work to settle under existing limits; the deadline is not an external cancel or hard kill. User Stop uses existing control/custody contract. Reserve control/settlement/final publication capacity even at zero. Explicit user extension/resume plus fresh authority is required. This bounds automatic turn permits, **not** tokens, dollars, tool calls or provider subagents; one turn can contain many operations. Show trustworthy usage/unknown separately. No distributed quota or new metering service.

A continuation carries only goal/task reference, exact reason, necessary changed evidence/wait reference and next action. Reuse current native session and existing MCP pagination; after compaction/Resume recover missing criteria from the bounded original request reference, not whole transcript/board. Avoid redundant status/report calls when an unchanged agenda is already covered; retain mandatory authority/report checks. Never truncate evidence/errors into a false pass. Passive observation, timers and UI reads make zero model calls.

## 7. Waiting and wakeup

Reuse task dependencies, review/clarification and runtime retry metadata first. Otherwise retain one bounded goal/task expected-wait record: kind, goal/task revision, typed exact external identity, authorized observer, last observation, next due time and original horizon. CI requires repository/run ID and expected commit or equivalent exact check identity, not a URL/string or success for another run. Extend the existing [strict Work Sync report](../../packages/legacy-agent-host/src/mcp/workSyncTools.ts) with an optional validated wait payload only if existing state cannot express it; preserve original command, agenda fingerprint and report token. No executable command, arbitrary callback URL, credentials or model-selected observer. A report requests observation, not proof of completion. Persist before acknowledging; repeated pending reports do not extend horizon or reset budget. Reassignment changes observer authority, not operation identity. Stop/scope change retires checks while retaining effect debt; external cancellation needs separate authority.

Use canonical dependency/review events. One authorized observer for a shared external operation; dependent obligations consume existing status. Wait is per obligation, not a blanket member/team flag: a member waiting for CI can execute another independent task. Missing/deleted/cyclic prerequisites and unassigned required work become actionable lead coordination, not indefinite waiting. Reuse board validation and bounded actual-cycle detection, not a DAG engine. A lead waiting on valid children need not poll their models.

Prefer trusted existing completion signals. Otherwise permit a single due read-only check using the designated agent's existing authorized tools and exact reference, with bounded backoff (proposed 5, 15, then at most every 30 minutes, respecting later Retry-After and original horizon). No CI polling service, GitHub App, webhook infrastructure or credentials. Trusted events can wake sooner; a check uses one shared permit only if it starts a model turn. Pending result advances due time, not the horizon/progress allowance; do not rerun CI for pending status. Failure/cancellation requires a new in-scope diagnosis; human approval wakes only on actual response. Unsupported observer/reference yields explicit attention, not guessed progress. Continue independent work. Horizon expiry shows exact reference and last-known state; pending CI is not a terminal task failure.

## 8. Recovery, cancellation and compatibility

Use the Stage 1 identity and receipt boundaries (Team, project, run, member, runtime instance/generation, input, authority revision). Stop/revoke atomically closes further admission; cancel unsent intents and keep unknown/consumed outcomes held until reconciliation. Already running work follows existing stop/custody contract. Retry original logical commands only when current owner can prove the allowed outcome; no blind restart or replay of an external action. Restart and resume retain objective, limits, receipts and wait state only under supported current owner/explicit user resume; a fresh relaunch is not a continuation of an old objective. Normal Quit follows #982's existing custody/cleanup contract; no hidden daemon, automatic reopening of a sealed session or claim that closing the app keeps agents working. After crash, read/reconcile retained intent and physical custody first; restore observation even when new execution is held. If automatic reconnection is not supported by a tuple, display recoverable attention and require explicit Resume rather than fake continuity. OS sleep cannot execute work; after waking, coalesce due observations, preserve elapsed deadline and avoid a catch-up flood. Never fall back to an unrelated project or stale provider session.

An unavailable member or failed dependency must not freeze other members/teams. The inspected [Host wake composition](../../packages/legacy-agent-host/src/composition/createRuntimeWorkSyncWake.ts) loops over member entries and the coordinator pump also awaits settlement; the scheduler already has per-team retained dispatch/timeout support, so do not introduce another global loop. Prove isolation of A vs B both within one team and across teams. If a member callback can block a sweep, adapt the existing bounded scheduler/pump to per-member single-flight work with bounded admission/fairness and retained physical settlement. Logical timeout does not release the original writer fence; no repeated replacement promises, no unbounded fan-out and no dropping original outcomes. A genuinely team-owned mutation may serialize members of that team until its canonical fence resolves; do not bypass it to fabricate isolation. Independent teams remain serviceable; surface the affected member/team and cause. Use existing recovery queue and strict read/error semantics. An unknown snapshot is not empty or idle. Observe/repair original debt even when new automatic admission is disabled. No automatic retry for permission denial, invalid configuration, unsupported capability or user Stop; attention must retain specific reason.

Qualify only supported current Stage 1 provider/mode tuples. Check actual Claude, Codex and OpenCode V1 support; do not promise capabilities merely from a version flag. Unsupported tuple: show explicit capability reason and preserve existing manual/legacy behavior, no unsafe fallback. On rollback turn off new admission but preserve state/receipt read and settlement; never remove a durable record while work or effects may be outstanding.

### 8.1 External effects and genuinely stuck runtime

Host receipts prevent duplicate supported Host admissions/submits; they cannot guarantee exactly-once arbitrary shell, merge, deployment or third-party MCP effects inside a model turn. Never replay a previous prompt or reassign work to repeat an ambiguous mutation after losing its result. Resume with fresh read-only reconciliation of the exact known operation when authorized (original PR/commit/run state); unresolved effects retain unknown and require concrete intervention, while independent work proceeds. Do not add a universal external effects ledger.

A long claimed/consumed/busy input cannot be declared idle just from elapsed time or absent logs. Use existing authoritative health/terminal/custody evidence and supported cancel/recovery. Observation expiry surfaces stuck/unknown attention; no automatic shared backing kill, fake terminal result or custody release. A known-no-start result differs from an unknown in-flight input. Keep running-app/awake-OS limitations explicit; no keep-awake daemon or process supervisor. Show actual execution/connection status rather than promise continuous work after the environment stops.
