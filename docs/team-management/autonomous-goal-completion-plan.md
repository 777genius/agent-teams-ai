## 1. Practical first release and scope

**User flow:** a user opens an already running, ready Stage 1 team, sends an explicit objective to its lead with **Continue until done** enabled for this request, and can leave it unattended. Use the existing lead composer/delegate submission and authenticated message receipt. Select one such production route for the first implementation; if the route is unavailable, expose capability rather than add a parallel entry point. Launch the team normally before using it. Do not also implement saved-template, task-start, scheduler, import, group chat or cross-team start variants in v1. Off means existing behavior. A saved preference never starts work on its own.

The first release covers a single accepted objective per execution-team incarnation/run lineage, lead and teammates, existing assignment/review/rework, normal continuation after a settled input, finite no-progress recovery, known waits (including authorized read-only CI checks), existing supported transient recovery and explicit Stop/Resume. Existing pending tasks outside the selected objective remain ordinary work. UI is one opt-in, one compact status, and existing Attention/controls; no new goal dashboard.

**Do not build:** second scheduler, task board, outbox, workflow engine, provider framework, quota service, transcript scoring, universal external effects ledger or external supervisor. Keep existing Work Sync, [work recovery plan](agent-work-recovery-implementation-plan.md), [D1 admission](agent-work-recovery-d1-runtime-admission-plan.md), [control plane](member-work-sync-control-plane-plan.md), and [Stage 1 migration](../plans/provider-migration/stage-1-legacy-host.md). Read current code rather than replay old checklists. No Stage 2/new Runtime/Orchestrator/OpenCode V2, closed-app or sleeping-OS execution, multi-goal/cross-team orchestration, provider substitution, new credentials or integrations, automatic merge/deploy/approval beyond actual original permission, mandatory reviewer or Git for non-code tasks. Do not modify #982 as part of this feature or enable default-on behavior. No promise that arbitrary models always solve arbitrary requests.

This is a bounded unattended run, not an always-on agent. Ordinary user input, manual controls, scheduled runs and non-opted-in teams remain compatible. Existing permissions apply unchanged.

## 3. Minimal state and ownership

| Existing owner | What it owns |
| --- | --- |
| Team owner / task and review stores | Goal acceptance, original scope and revision, task association, final proposal/acceptance, shared permits and existing delivery receipts |
| Work Sync | Derived eligible obligations, progress/wait classification, decision and finite recovery |
| Runtime owner/provider | Current binding/input/operation, admission and claim, terminal and custody evidence, stop/resume |
| Runtime recovery | Classified provider errors and retry-at-reset; no competing ordinary continuation |
| Desktop/MCP | Explicit user start/control, bounded lead/report commands, read-only projection |

Use **one** small Team-owned objective record and existing canonical task linkage (a root-task field only if it provides all required invariants). Store goal ID, immutable original user request/message receipt reference (retain bounded original text/criteria if the reference can expire), execution scope and run lineage, user scope revision, mode/deadline/permit limit, disposition, optional final proposal/result reference. Keep permit witnesses in existing continuation/delivery receipts. No duplicated task inventory, full transcript, second event journal or per-goal database. Derive board/agenda state on demand via existing bounded reads. Persist only needed per-obligation progress/wait data in existing Work Sync state.

| Canonical goal disposition | Meaning |
| --- | --- |
| active | Runnable work, expected wait or recoverable attention; per-obligation reasons are a projection |
| finalizing | Exact lead proposal exists; close its new admissions, observe required input settlement and compare evidence |
| accepted | Immutable acceptance; original final publication may still be pending/unknown |
| stopped | User stop/revocation or explicit abandon; no new auto-admission, original debt retained |

Completed is accepted + final result durably available. Budget/approval/unsupported/unknown are typed reasons on existing active/stopped state, not a new state machine per reason. Manual pause uses existing controls/latch, not another pause flag. Goal revision changes only by explicit user scope change; derived task/evidence revisions remain separate.

Intake uses the exact authenticated lead-directed message/delegate command receipt; same ID/payload replay returns the original goal and first input, different payload conflicts. Persist acceptance and first lead obligation through existing owner recovery before acknowledging; if the initial message was admitted but the result was lost, reconcile its original delivery, not a fresh user prompt. The user request limits authority; model-generated criteria do not grant permission to merge/deploy/spend or widen project access. Material ambiguity becomes clarification while independent work proceeds.

A stable goal association is captured by the canonical Team owner from the original goal-bound input/command. [TaskStartCause](../../packages/legacy-agent-host/src/team/TaskStartCause.ts) already binds task-start command/message/delivery/input/runtime; [TeamCommand](../../packages/legacy-agent-host/src/team/contracts.ts) does not itself expose a goal association. Extend only missing private metadata. Descendants, task notifications, review/rework inherit the authorized association; no guessing by assignee, title, chat text or recency. No automatic enrollment of unrelated backlog; explicitly attaching an old task is deferred in v1 unless the existing owner has a safe explicit association path. Peer/group/cross-team/ordinary user input remains ordinary unless original provenance proves goal scope. Ambiguous provenance must not become goal authority. Same-team reassignment/roster edit retains goal and budget while invalidating obsolete bindings. No clone/import/new launch adoption. Supported Resume binds a proven successor and reconciles original debt first.

Required scoped work is monotonic except explicit user-authorized scope removal or a linked replacement; task deletion alone does not erase an obligation. Use existing task history/metadata; if those are insufficient, add only the minimal persisted association/tombstone needed. Do not reinterpret legacy board completion globally.

## 4. Lead obligations and completion

Work Sync's existing agenda remains the task/review truth. Derive only three additional lead reasons: plan/coordinate missing work; resolve required rework/assignment/clarification; verify/finalize. Waiting for valid children is **not** an actionable lead obligation. An empty board may require planning, or may be a legitimate task-free request. No synthetic management tasks, second board or required review for every simple request. Use existing review and user approval rules. A completed task, empty agenda or ordinary final chat text is not objective acceptance.

### 4.1 Finalization is a proposal, not a synchronous completion

Use one narrow lead-only finalization command: reuse an existing path if it can bind the goal, otherwise one strict command for the lead's result, acceptance criteria and relevant evidence references. The current member_work_sync_report does not complete tasks. The command records an immutable proposal under the original goal-bound input and lead authority. It returns promptly; it **does not wait for its own native turn to end**. Do not publish this proposal as accepted completion. Ordinary progress/user messages retain existing semantics; the finalization result must not generate a duplicate ordinary final message.

The following quiescence requirement is mandatory (confirmed [controller setTaskStatus](../../agent-teams-controller/src/internal/tasks.js#L342-L380) updates task status and follow-ups without checking native input settlement; CodeRabbit review on #1315 correctly identified the resulting race):

- Before committing acceptance, every required goal-bound input capable of affecting the accepted result (including the lead's proposing input, teammates, reviewers and retained generations) must have a canonical terminal outcome, or be proven never started/cancelled before claim. Claimed, consumed, unknown, pending interactions and outstanding relevant effects block acceptance. A historical failure is not permanently blocking if its effect is resolved and required work has a proven successful replacement. A runtime session may remain allocated but idle; there is no requirement to terminate it.
- On proposal, close new goal-driven admissions for that exact candidate, **without** interrupting already claimed work or blocking ordinary controls. Cancel/retire only superseded unsent automatic intents through existing guards. Continue to observe relevant receipts. Wait for the proposing lead turn and required mutating inputs to settle. Do not wake the lead just to ask if its own turn has settled. If an unfinished required task/review/new scope or new material evidence makes the proposal invalid, discard it and resume only after fresh authorization/decision; do not freeze runnable work waiting on an impossible acceptance.
- Compare the candidate's goal revision and relevant canonical task/review/evidence fingerprint after quiescence. A later edit, artifact revision, new required task, rework or unresolved effect invalidates it. A successful terminal input by itself is not proof of task success. Verify required check references against the exact accepted artifact/commit revision; subjective criteria use accountable lead attestation with limitations, not invented independent verification. If an unrelated input is known to modify the same required result, it also invalidates the candidate; the system cannot guarantee protection from arbitrary external writers. No new universal filesystem lock, workspace scanner or global team idle barrier.
- Commit acceptance via a short existing Team-owner guarded mutation after proving a stable closed-admission candidate and exact current evidence. Do not take a Team lock across a Runtime/network await. Any uncertainty in the cross-owner proof holds the candidate. User Stop/pause, revoked authority or scope revision wins before acceptance; a late proposal/settlement cannot clear it. The goal may be resumed only through existing explicit control. No second model turn when the proposal already contains a valid result and all conditions settle.

### 4.2 Result delivery and meaning of success

Acceptance freezes the revision and closes objective-driven work. Persist acceptance and original final-result publication obligation using existing command/message receipts. Keep the immutable accepted result visible as result pending delivery until durably available in the existing user channel; unknown publication is reconciled by the original ID/payload, never a new generated answer. Do not require the user to read the message or the renderer to be mounted. Result publication and cleanup do not use a turn permit. A new goal after acceptance is an explicit start, not reopening old history. If any required criterion is failed, skipped, stale, awaiting approval or uncertain, show the exact outstanding reason instead of success.

Do not allow deleting a failed required task to manufacture completion. Existing canonical deletion/replacement history must retain the unmet obligation until a valid linked replacement or explicit user-authorized scope removal. Existing review requirements remain authoritative; no bypass of self-review, stale review or human approval.

## 5. One continuation path

Reconcile after authoritative settled input, task/review/dependency change, recovery result or due wait; use existing bounded fallback scheduler. [RuntimeActivityCoordinator.observe](../../packages/legacy-agent-host/src/runtime/RuntimeActivityCoordinator.ts) validates original Host/session/input/operation and stores terminal state before projection. Use durable Runtime facts; logs, UI idle, Stop hooks, missing events and delivery acknowledgement are only signals. Recover missed events by level-triggered reads, not replaying all history.

| Current fresh state | Decision |
| --- | --- |
| stopped, revoked, stale/unknown binding, exhausted deadline/permits | No new automatic claim; retain exact reason and settle original debt |
| claimed/consumed input, approval/control pending, admitted eligible next input | Observe existing input; no duplicate nudge |
| valid finalizing candidate | Wait for relevant terminal facts, validate and publish original result; no extra model turn |
| actionable work, current idle/settled runtime, allowed admission | One next-turn intent through existing receipt/outbox and Runtime claim |
| verified dependency/wait or retry-at-reset | Observe due event; no blind retry |
| retryable terminal provider failure | Existing recovery owner, not parallel normal continuation |
| no runnable work, goal open | Explain pending dependency or unresolved coordination; never infer completion |

Use current Work Sync planner and [Host composition](../../packages/legacy-agent-host/src/composition/createHostWorkSyncComposition.ts), not another orchestrator. The existing [TeamWorkSyncCommands](../../packages/legacy-agent-host/src/work-sync/TeamWorkSyncCommands.ts) and [native message ports](../../packages/legacy-agent-host/src/work-sync/createNativeWorkSyncMessagePorts.ts) require actual original native input/sender proof; a post-turn wake cannot fabricate it. Probe existing private Team system-notification/receipt path first. If necessary add **one** narrowly typed Host-owned continuation command through canonical Team delivery authority and existing Runtime input admission; do not expose a general system sender or pass forged MCP actor/token. The exact gap in #982 is an observation pending product E2E, not permission to rewrite its contracts.

One logical pending automatic intent per member/current runtime authority. The identity binds the goal revision, exact target binding, original terminal input/operation (or canonical new task/wait cause) and selected actionable obligation. Choose a stable cause once; persist immutable payload and consumed witness in existing receipts. Coalesce duplicate causes from board/task/review/wake/settlement; new work arriving after that cause remains eligible for a later decision. Existing queued input covers an obligation only with matching original provenance. An unrelated foreground message does not grant goal authority or permanently suppress it. Respect existing queue ordering; no direct provider submit or second outbox. Missing/pruned source proof means hold, not "new" event.

[TeamDeliveryAuthority](../../packages/legacy-agent-host/src/team/TeamDeliveryAuthority.ts) already verifies receipt, role, binding, content and fingerprint. Any new private provenance variant must be covered by those checks without modifying historical fingerprints. [RuntimeOwner](../../packages/legacy-agent-host/src/runtime/RuntimeOwner.ts) owns admit, lookup, cancel and durable dispatch claim. Revalidate current goal/revision/recipient, grant/control, custody/readiness, pending approval, permit and original cause at admission and actual claim. Use short existing owner operations and durable receipt/reconciliation between owners; never hold a Team/Runtime lock across external IO or acquire mutually waiting locks. Stop/pause/authority revocation closes the actual claim gate, cancels eligible unsent intents, retains uncertain ones. A claim before closure may have physically entered handoff; use existing cancellation/custody proof, never mark it not-sent by assumption. Do not relax this for a recovery nudge. Read-only UI/diagnostics make no mutations; existing authorized forceNudge is subject to the same opted-in admission gate.

Goal-bound normal continuation, task/review/board notification, peer wake and runtime recovery must share the same permit/claim rules; preserve original inbox and delivery history rather than suppressing ordinary communication. A supported producer with no goal provenance must remain ordinary and cannot create goal-specific work. If an automatically started goal-bound path lacks trustworthy admission/claim provenance, that provider/mode is not qualified. Existing direct authenticated user messages and ordinary unrelated work keep their existing behavior.

## 6. Progress and resource limits

Separate three causes of a new turn: eligible productive continuation, recovery after no verifiable progress, due read-only observation of an expected wait. First planning/pickup is ordinary once per new obligation; use existing two-attempt recovery allowance per actual stalled episode, not two turns per whole task. Existing task/review/dependency revision and task-change evidence are the progress sources. A long in_progress task can count a new relevant durable substep; a research task can count a new bounded result/checkpoint reference. Prefer existing tools/evidence, no new progress-report protocol unless a specific gap is demonstrated. A checkpoint is a claim unless backed by actual observable change/result; a report, heartbeat, tool call, timestamp, state toggle or same failing check never alone replenishes recovery. If progress is unobservable, finite recovery then attention is safer than unlimited guessing. No full transcript scoring. Independent member/item progress must not refill a stuck episode's allowance; changing clocks/restarting or making duplicate tasks must not reset the shared bound.

**Initial proposed preset (validate in canary):** 12 elapsed hours, 100 automatic-turn permits per goal shared by lead and members. User can set/extend these explicitly; 100 is not a promise of sufficient capacity for every team. One shared finite deadline and limit; do not add per-provider token budgets or complex allocation UI. Count each goal-bound non-human-triggered new native input that can start a turn (including task/review/board/peer wake, due observation and runtime retry), not existing receipt replay/inbox insertion, direct user input, passive observation, control/cleanup or final publication. Reuse existing durable intent/receipt as permit witness; no new standalone permit ledger. Reserve atomically by the current Team owner before admission so concurrent members cannot exceed the shared bound, consume once at the actual claim, return only on proven no-start; hold on unknown. A retry of the same immutable transport identity is not another permit. If current owner cannot prove the shared accounting, keep the feature unqualified rather than implement a global quota system. A scope edit or reassignment cannot reset spent permits.

At expiry/exhaustion stop new automatic claims, keep ordinary message history and original obligations, let already claimed work settle and preserve control/settlement capacity. Do not terminate an external process or drop queued work simply because the timer ended. User Stop is distinct, using existing immediate control/cleanup. Explicit extension/Resume performs a fresh check, no catch-up flood. Permit count is not a hard money, token, subagent or tool-call limit: one turn can invoke many operations. Show trustworthy existing usage, incomplete usage explicitly. Reuse existing provider-side limits.

No new prompt engine. Wake input is just goal/task reference + specific next action + necessary changed evidence or wait reference. Reuse the native session and existing MCP reads; never append full task board/transcript on every continuation. On compaction/Resume, recover missing original goal criteria with the existing authorized context/read route; keep existing mandatory report and authority checks, avoid redundant status calls for unchanged accepted evidence. Passive reads/ticks consume zero model turns. On current parent, [TeamContextReminders](../../packages/legacy-agent-host/src/team/TeamContextReminders.ts) and [inputPreparation](../../packages/legacy-agent-host/src/runtime/inputPreparation.ts) retain exact original input/preparation and represented context-epoch proof. Use the same bounded recovery path after compaction, not an extra standing context message; goal reference never displaces mandatory role/permission instructions or changes an admitted fingerprint. Respect the existing 1 MiB Team state and reminder/input byte limits from the parent plan. Do not store a full board/goal transcript in every receipt. Retention/compaction must not discard unresolved intents, spent permits, required task obligations or final proposal/receipt; test the configured maximum run and existing capacity boundaries. If current storage hits its safe limit, surface attention; do not add new retention infrastructure speculatively.

## 7. Expected waits and useful progress

Use existing dependencies, review/clarification, approval and retry-reset metadata first. Only when absent add a bounded task/goal wait to existing Work Sync state and an optional validated field on its existing report. Exact operation identity (e.g. repository/run/expected commit), current goal/task revision, one authorized observer, last status, next due time and original horizon. No executable payload, arbitrary URL, credential or new callback API. Agent report requests observation; it is not evidence of external completion. Persist before acknowledgement; repeat report of the same pending operation cannot reset horizon/attempts.

Prefer existing trusted events. Otherwise, if the agent already has an authorized check tool, allow one read-only due observation of that exact reference through the same turn gate. Proposed backoff 5, 15, then at most once per 30 minutes, respecting later provider Retry-After and original horizon. Coalesce duplicate signals and missed wakeups after sleep; one observer per external operation. No generic CI integration, polling engine or webhook service. Human wait wakes only on actual response; unsupported observer/reference produces concrete attention. A pending CI run is waiting, not failure, and never by itself authorizes rerun. Failed/cancelled run requires a new in-scope decision. Reassignment updates observer authority, not operation identity/horizon. Stop/scope change retires future checks but preserves unresolved effects and does not cancel external operations without separate authority.

Wait belongs to the obligation, not the whole member or team: another eligible task proceeds. The lead waits for valid children without polling them. Missing/deleted/cyclic prerequisite and unassigned work are coordination obligations, not indefinite dependency wait. Reuse existing graph checks; no general DAG engine. A horizon expiry reports exact last-known condition and budget disposition, not false blocker/failure. The user must see waiting versus action required distinctly.

## 8. Recovery and isolation

Keep existing Team/Runtime binding, run/member/generation, operation ID, receipt, custody and authority fences. Crash/restart reconciles original accepted intent before new effects; no repeated admission on ambiguous acknowledgement. Normal Quit still performs #982's existing cleanup; no hidden daemon or automatic reopening of sealed sessions. Only supported current owner/explicit Resume may restore the same goal and budget. Fresh relaunch is a new run. OS sleep cannot execute work; on wake preserve elapsed deadline, coalesce due checks. Show actual execution/connection state. Unsupported provider mode or failed readiness has explicit attention and ordinary manual path, never unsafe fallback.

The existing [Host wake composition](../../packages/legacy-agent-host/src/composition/createRuntimeWorkSyncWake.ts) and coordinator pump await member settlements; existing scheduler already has bounded per-team retained dispatch/timeout. Reuse it. First reproduce an actual stuck callback preventing unrelated progress; adapt only that path to bounded per-target single-flight work. No second timer/scheduler, unrestricted Promise fan-out, repeated abandoned promises or releasing a physical writer's fence on logical timeout. If a true canonical Team mutation must serialize members, expose the hold; independent teams remain serviceable. Reconcile old debt even with new admission disabled. No auto retry for permission denial, explicit Stop, unsupported capability or invalid config.

**External side effects are not exactly-once merely because Host inputs are.** A lost arbitrary shell command, remote merge, deploy or third-party MCP response is not proof of no effect. Do not resend the old prompt or reassign an ambiguous mutation for blind repetition. First reconcile exact known reference through an authorized read-only query; otherwise retain unknown and request a concrete decision while independent work continues. Existing retryable known-no-start/provider reset is different from unknown in-flight work. A busy/claimed/consumed input with no recent logs is not safely idle; existing health/terminal/custody evidence and supported cancellation apply. Observation timeout only surfaces stuck/unknown attention, never kills a shared backing or fabricates success.

Qualify actual Claude/Codex/OpenCode V1 supported role/mode tuples only. Do not claim all providers based on exported types or protocol flags. Rollback disables new automatic admission but preserves goal/receipt readback and original settlement. No production activation before required gates.
