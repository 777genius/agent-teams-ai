## 4. Lead obligations and completion

Work Sync's existing agenda remains the task/review truth. Derive only three additional lead reasons: plan/coordinate missing work; resolve required rework/assignment/clarification; verify/finalize. Waiting for valid children is **not** an actionable lead obligation. An empty board may require planning, or may be a legitimate task-free request. No synthetic management tasks, second board or required review for every simple request. Use existing review and user approval rules. A completed task, empty agenda or ordinary final chat text is not objective acceptance.

### 4.1 Finalization is a proposal, not a synchronous completion

Use one narrow lead-only finalization command: reuse an existing path if it can bind the goal, otherwise one strict command with the result and current evidence references. member_work_sync_report does not complete tasks. Reject a proposal immediately with the specific missing required work/approval/evidence if the current snapshot already proves it incomplete. Only a candidate otherwise ready for acceptance enters finalizing and closes new goal-driven claims. Persist the immutable proposal bound to the original lead input and goal revision; return promptly, **never wait for the proposing input from inside its tool call**. One pending candidate, no second proposal queue. The lead's normal progress messages remain visible; only the acceptance receipt produces the authoritative final result. Do not publish provisional text as a completed goal.

The following quiescence requirement is mandatory (confirmed [controller setTaskStatus](../../agent-teams-controller/src/internal/tasks.js#L342-L380) updates task status and follow-ups without checking native input settlement; CodeRabbit review on #1315 correctly identified the resulting race):

- Before committing acceptance, every required goal-bound input capable of affecting the accepted result (including the lead's proposing input, teammates, reviewers and retained generations) must have a canonical terminal outcome, or be proven never started/cancelled before claim. Claimed, consumed, unknown, pending interactions and outstanding relevant effects block acceptance. The proposing lead input must itself settle successfully; a failed/cancelled/unknown proposing turn cannot certify its candidate. A historical failure is not permanently blocking if its effect is resolved and required work has a proven successful replacement. A runtime session may remain allocated but idle; there is no requirement to terminate it.
- On a valid proposal, close new goal-driven claims for that candidate, without interrupting claimed work or blocking ordinary control. Retire superseded unsent wakes through the existing guards; retain the underlying task obligations. Observe the proposing input and other relevant mutators to settlement. If new/reopened work, a failed proposing input or a relevant evidence change invalidates the candidate, retire it and return to active under the **same** accepted scope and remaining budget; re-evaluate automatically. Do not require the user to say continue merely because verification became stale. User Stop, pause, revocation, a material scope change or actual exhaustion is different and cannot be cleared by the candidate. Unknown settlement stays finalizing with visible attention, not a busy retry loop. Do not wake the lead just to wait for its own terminal event.
- Compare the candidate's scope revision and relevant canonical task/review/evidence fingerprint after quiescence; exclude presentation, read counters and unrelated history. A relevant edit, new required task, rework or unresolved effect invalidates it. For code, bind final checks to the exact commit/artifact the user requested, not merely a green check or mutable workspace timestamp. Known concurrent writers to that result must settle or be isolated by existing worktree boundaries; if the current evidence cannot distinguish them, hold that candidate rather than claim the working directory was frozen. No global team idle barrier, filesystem watcher or new lock for arbitrary external writers. Subjective evidence is lead attestation with limitations, not independent verification.
- Commit acceptance via a short Team-owner guarded mutation after proving the closed-admission candidate and exact current evidence; never hold a Team lock across Runtime/network await. Uncertainty holds the candidate. Stop/pause/revocation/scope edit ordered before acceptance wins; already accepted results can still publish through their original receipt after Stop. Deadline closes new automatic claims; attempt exhaustion closes new authorizations (not already charged valid claims). Neither prevents acceptance of a still-valid already-produced result after its terminal proof. No additional model turn is needed in that case.

### 4.2 Result delivery and meaning of success

Acceptance freezes the revision and closes objective-driven work. Persist acceptance and original final-result publication obligation using existing command/message receipts. Keep the immutable accepted result visible as result pending delivery until durably available in the existing user channel; unknown publication is reconciled by the original ID/payload, never a new generated answer. Do not require the user to read the message or the renderer to be mounted. Result publication and cleanup do not charge an automatic attempt. A new goal after acceptance is an explicit start, not reopening old history. If any required criterion is failed, skipped, stale, awaiting approval or uncertain, show the exact outstanding reason instead of success.

Do not allow deleting a failed required task to manufacture completion. Existing canonical deletion/replacement history must retain the unmet obligation until a valid linked replacement or explicit user-authorized scope removal. Existing review requirements remain authoritative; no bypass of self-review, stale review or human approval.

## 6. Progress and resource limits

Use only three reasons for a new automatic input: productive next action, recovery after no verifiable progress, due observation of a registered wait. Choose existing eligible task/review/lead obligations; do not create a parallel plan graph. The current [RecoveryHealth](../../packages/legacy-agent-host/src/work-sync/policy/core/domain/MemberWorkSyncRecoveryHealth.ts#L216-L315) mainly treats entering in_progress as progress; [allocator](../../packages/legacy-agent-host/src/work-sync/policy/core/application/MemberWorkSyncRecoveryAllocator.ts#L60-L97) counts reservations over the current episode coverage. Preserve the existing ordinary non-opt-in behavior. For opted-in goals, use the existing task/assignee/review-cycle or lead-obligation episode identity: an initial eligible action once, then each successful relevant new durable evidence point permits another productive turn. Use actual task/review/dependency changes or task-change/check evidence with original reference; mere write volume, repeated reports, status toggles, timestamps, a green check for an old commit, and a new task invented just to reset a counter do not qualify. Long in_progress work and research can count a relevant new sub-result tied to the current task using already available artifacts/results; no mandatory commit, new model verifier, or transcript scoring.

When the model ends a turn before completing the obligation and no new evidence is available, give the existing bounded two recovery attempts (not two turns for the whole task), with a compact concrete next action. An accepted still_working lease is not evidence that an already-settled input is running; a stale lease must not suppress the qualified next action. Never interrupt a genuinely active input. A new evidence-backed step resets only its own no-progress episode, not unrelated stalled work or the shared attempt bound. If an item exhausts recovery, retain visible attention for it and allow other eligible work, including a useful lead coordination decision. Reassignment does not silently turn an unknown external mutation into new work. A provider that cannot supply adequate evidence can safely hold after bounded recovery; do not promise unobservable productivity. If lead repeatedly produces invalid final candidates, debit recovery as no progress rather than create unlimited finalization attempts.

**Proposed first preset (validate in canary):** 12 elapsed hours and 100 automatic input attempts per goal shared by lead and teammates. User can explicitly set/extend the bound. One deadline and counter, not a quota subsystem. Charge one attempt **once at durable authorization of a distinct automatic input intent, before Runtime admission**, using the existing Team owner receipt/recovery boundary. The same immutable transport retry/replay never charges again. Count goal-driven task/review/board/peer wakes, productive/recovery turns, due checks and provider retries that create a new native input. Direct authenticated human input, passive observations, mere inbox rows, control/cleanup and final-result publication are not attempts. Serialize charge against remaining budget with the original receipt; if charge/publication uses recoverable steps, hold new admission until the original debit/intent is established. Never permit a crash between counter update and receipt to debit twice or start uncharged work.

At most the charged bound can start; display attempt limit/used/remaining accurately, optionally actual starts from existing telemetry. Avoid a cross-owner reserve/consume/refund ledger and recycling permits after ambiguous outcomes. If a user extends the limit, only the explicit new bound changes. This trades occasional unused capacity for simpler crash correctness; make the reason visible. Retain existing per-obligation recovery limits independently.

With zero remaining, allocate no new attempts; do not accidentally reject the last already-authorized input because its own debit reached zero. Stop/revocation/finalization still close its claim. Retain ordinary history and original obligations, let earlier claimed inputs settle and preserve control/final publication capacity. Never terminate an external process on budget exhaustion. User Stop is separate, using existing immediate control/cleanup. Extension/Resume performs a fresh check, no catch-up flood. This is not a hard money/token/subagent/tool-call cap: reuse existing provider limits and show trustworthy usage, incomplete usage explicitly.

No new prompt engine. Wake input is just goal/task reference + one specific next action + necessary changed evidence or wait reference. Use a short instruction to do the next required step, not merely report status; report a legitimate wait/needed approval, then yield. A continuation cannot silently broaden original permissions. Reuse the native session and existing MCP reads; never append full task board/transcript on every continuation. On compaction/Resume, recover missing original goal criteria with the existing authorized context/read route; keep existing mandatory report and authority checks, avoid redundant status calls for unchanged accepted evidence. Passive reads/ticks consume zero model turns. On current parent, [TeamContextReminders](../../packages/legacy-agent-host/src/team/TeamContextReminders.ts) and [inputPreparation](../../packages/legacy-agent-host/src/runtime/inputPreparation.ts) retain exact original input/preparation and represented context-epoch proof.
