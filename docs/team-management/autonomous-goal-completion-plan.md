# Autonomous goal completion: Work Sync on Stage 1 Host

**Status:** reviewed design proposal (six self-review passes; independent implementation review and E2E pending), implementation not started. **Parent:** [#982](https://github.com/777genius/agent-teams-ai/pull/982), inspected at `dee94bf14ddbe81143ed2c3c9029a74e66158e1e` (2026-11-27). This is a follow-up, not an amendment to the migration acceptance or authorization to merge/activate it. **Target:** a team with a lead and teammates can finish an explicitly accepted user objective unattended while its supported desktop/Host execution environment is running.

## 1. Decision and scope

Extend the existing Work Sync policy and the Stage 1 Host's current Team/Runtime owners. Do not build a second scheduler, task board, message dispatcher, recovery ledger, workflow engine, external supervisor, or provider framework. The existing [work recovery plan](agent-work-recovery-implementation-plan.md), [D1 admission plan](agent-work-recovery-d1-runtime-admission-plan.md), [control plane](member-work-sync-control-plane-plan.md), and [Stage 1 plan](../plans/provider-migration/stage-1-legacy-host.md) remain relevant. Read the current implementation rather than implementing their historical checklists again.

An explicit run-level opt-in, **Continue until objective is done**, selects this behavior. Off preserves current behavior. Use existing team settings/launch controls and Attention/readback if possible; one compact mode/status surface, not a new page. One active objective per selected execution team/run in the initial release. Scope is that objective, not every unfinished task in the logical team, other projects, or unrelated backlog. The user authorizes the work, tools and optional external actions; autonomous mode never broadens them.

In scope: lead planning, task pickup, task work, assigned review and changes requested, coordination, final acceptance, normal turn continuation, bounded lack-of-progress recovery, supported temporary error recovery, durable expected waits, recovery/reconciliation after supported restart, stop and visible disposition. Existing task/review workflow stays canonical. Keep ordinary user chat, manual retry, existing schedules, native permissions and non-opted-in teams compatible.

Out of scope: closed-app/OS sleep/power-loss execution, new Orchestrator/Runtime v3 or OpenCode V2, multi-goal orchestration, remote agents, arbitrary integrations/webhooks, autonomous model/provider substitution, auto-approval, auto-merge or deployment without original permission, mandatory model-based verifier, semantic analysis of every transcript, generalized checkpoint engine, rewriting old legacy paths, release/default activation. A running but disconnected/failed Host cannot promise progress until it is recovered. No claim that any model always solves any objective.

## 3. Ownership and minimal persisted data

| Owner | Responsibility |
| --- | --- |
| Team owner / task and review stores | Authoritative objective acceptance, membership and task state; scope, goal revision and final acceptance |
| Work Sync policy | Derived eligible obligations, wait/progress classification, next action and bounded continuation/recovery policy |
| Existing Work Sync persistence and outbox | CAS, one logical pending continuation, deduplication and durable retry/unknown disposition |
| Runtime owner/provider adapter | Current session/input identity, busy/settled observation, next-input admission, Stop/Resume, custody and terminal proof |
| Existing runtime recovery | Classified provider failure/retry-at-reset; no second ordinary continuation producer |
| Desktop/MCP | Explicit opt-in, bounded commands and read-only status; no separate runtime or goal truth |

Use one small durable Team-owned objective record, not an execution engine. Existing root-task metadata is acceptable only if it proves the same ownership, revision, scope and deletion invariants; otherwise add one record alongside the existing canonical Team state. Suggested fields (reuse names/types already present): `goalId`, original accepted request/message or task-start reference, execution-team incarnation and authorized run lineage, immutable accepted criteria/reference, `revision`, mode, deadline and turn budget, disposition, final result/evidence reference. Store immutable original request by reference when already retained; if the referenced content can expire, retain its bounded immutable criteria/text until goal retirement. No whole-transcript copying.

Use one stable goal association on a task (or an existing equivalent root-task linkage). Capture it from the original admitted goal-bound input, not mutable selected team/UI state or model-provided arbitrary goal IDs. In-scope descendants inherit only under the same authority; review/rework/reopen retain the association. Explicitly attaching existing work needs an authorized command; a new ordinary user task or unrelated scheduled run must not accidentally join. A goal cannot move across logical/project team instances, imports, roster replacement or fresh launches. A supported Resume may rebind to its proven successor generation using the current owner; it cannot adopt another goal. Preserve other teams' existing task links and cross-team messages, but do not auto-enroll other teams in this first release. If an existing dependency is external to this execution team, observe its authorized existing state, not execute or claim it automatically.

The objective's required work is monotonic except for an explicit user-authorized scope revision. A lead may refine the plan or add required in-scope work, but cannot delete/drop a requirement to manufacture success. Deleted tasks leave an unmet obligation until replaced with an explicit linked successor or removed by the user; no permanent duplicate task inventory. Use canonical task history/metadata to preserve that relationship; if the current stores cannot enforce it, the minimal durable association is part of slice C. Avoid a new task store, generic graph or storage migration without a demonstrated invariant.

At intake, bind the accepted user request and the opt-in/limits to the exact existing launch or task-start command receipt before acknowledging autonomous start. Replaying that receipt must return the same goal, not allocate a second goal; a same-ID different payload conflicts. Persist the objective and task-start obligation through the existing owner transaction/receipt recovery; a crash between acceptance and first lead input must leave visible pending work, not an acknowledged empty goal. The lead initially has a planning obligation even if no tasks exist. When the lead creates work for this objective, bind the tasks to its ID under canonical authority. Explicit user edits revise the objective; stale decisions must not act on the newer revision. Ordinary user chat must not silently replace or extend it. An additional objective is deferred or requires an explicit replace/stop, not merged into the existing one by guessing.

## 4. Completion semantics

A turn ending, a model claiming success, an empty per-member agenda or even all board rows reporting completed are not proof of objective completion. Derive the lead's action from the current goal scope:

- Plan/clarify the accepted work and materialize missing required tasks.
- Assign actionable unowned work; resolve broken dependencies, review changes and questions directed to the lead.
- Wait for active delegated work while still doing independent obligations; avoid waking the lead for every child event.
- After required work is finished, run final verification against the current objective criteria and task/review/evidence revisions.
- Persist the final acceptance outcome and publish one final result to the user, using existing message delivery and idempotency.

Require the accepted goal revision, all required tasks successfully resolved, no required outstanding review/rework/approval/wait or unresolved relevant effect, and a current lead final attestation with relevant evidence. Use existing task verification and review if available; do not force a second verifier into every run. Mark completion only after final result is durably recorded and publishable through the existing channel. Cancelled/deleted tasks are not successes; explicit user-authorized scope changes can remove obligations. An unresolved required outcome prevents completion, not unrelated independent work. The lead may propose a new follow-up task within the scope; user authorization is required for expansion. Never invent missing evidence. Where a criterion requires human judgment, ask the user and retain independent work.

### 4.1 Lead obligation projection (not another task list)

Derive at most the following reasons from the canonical goal and board: `plan_required`, `assignment_or_clarification_required`, `review_or_integration_required`, `waiting_for_required_work`, `final_verification_required`. Use a small tagged state/decision, not synthetic tasks for every management event. If the team is waiting only on valid children, do not continually nudge the lead. If no owner can act (missing member, broken/cyclic dependency, unassigned task, rejected plan), make it actionable for the lead once with the specific cause. Do not silently assign a task to the wrong member or grant new permissions. Coalesce board-complete notification and the derived final obligation: the existing canonical notification can wake the lead, but cannot close the objective.

### 4.2 Acceptance is revision-bound

Use the existing review/verification authority where present. Keep a compact final attestation referencing accepted criteria, required task IDs/revisions, current review cycle/evidence (e.g. CI run and exact commit), and final result. It is an accountable lead judgment, not a universal automatic proof of semantic correctness. Do not treat a generated checklist as independent verification or require the same expensive verifier for every kind of task. Unknown/unsupported evidence remains explicit; when a criterion cannot be checked, the goal is not certified complete. Never require Git/CI for a non-code objective. Compare against a fresh canonical goal and relevant task/evidence revision under the Team owner fence before accepting; if rework, a new required task, scope edit or stale result arrives between verification and acceptance, discard the stale decision and re-evaluate. No self-review bypass.

Use the existing user-facing message/outbox identity for the final result. Persist acceptance plus the final-message obligation with the existing atomic publication or recoverable command pattern; distinguish `result_pending_delivery`, `completed` (durably available to the user in the existing channel), and `delivery_unknown`/attention if outcome is not established. An inbox/message row idempotency key is not proof the user has read the result. Recovery must complete original publication or show unknown; never generate a new final answer just because its acknowledgement is lost. After acceptance, ordinary new messages/tasks do not reopen the completed goal; an explicitly revised/new user objective requires fresh authority. Preserve readback of accepted and unfinished obligations.

## 5. Continuation decision

Use one decision per current objective/member/settled input, with current authority, not chat-text heuristics. Reconcile on authoritative settlement, task/review/dependency changes, recovery result, due wait and bounded fallback observation. Debounce/coalesce repeated events; events are triggers, not proof. Reuse the scheduler and current Team/Runtime feed. No new periodic LLM calls while an agent is busy or idle with no actionable work.

| Fresh snapshot | Action |
| --- | --- |
| Exact current runtime busy or approval pending | No new input; retain obligation |
| Settled current input; eligible work, permitted mode and budget | Plan one next turn through existing admission/outbox |
| Review/clarification now actionable | Wake the authorized owner/reviewer/lead through the same policy |
| Waiting on a verified dependency or registered wait | Record wait; no blind continuation |
| Retryable provider failure | Delegate to existing runtime recovery; no concurrent normal continuation |
| Missing identity, stale/partial snapshot, unknown effect | Reconcile; do not start another effect on that binding |
| Stop, explicit pause, permission revoked, limits exhausted | No automatic turn; keep typed reason and unfinished work |
| Nothing eligible, goal still open | Observe next event; classify unresolved responsibility or waiting; do not infer success |
| Goal accepted as complete | Do not schedule further work; deliver final result once |

Implement a small pure decision helper only if the existing Work Sync policy cannot express these distinctions. Keep deterministic rules and narrow ports; no provider-specific logic in the core. Re-read canonical state under the existing admission guard immediately before dispatch, including goal/task revision, member identity, runtime instance, completed input/generation and control revision. A late event from an old generation is diagnostic only. No direct sends or fabricated agent commands. Normal continuation needs an existing supported Host-side system command authority. The inspected [TeamWorkSyncCommands](../../packages/legacy-agent-host/src/work-sync/TeamWorkSyncCommands.ts) and [native message ports](../../packages/legacy-agent-host/src/work-sync/createNativeWorkSyncMessagePorts.ts) require original native input/sender authority; they cannot simply be called with a fabricated MCP proof after a turn has settled. First see whether an existing Team-owned system notification/command can carry the exact authorization. Otherwise add one narrow **private** Host-owned continuation command, behind the existing Team write/receipt and delivery authority, with immutable goal/revision/target/settlement binding. Do not expose a generic system sender to MCP or reuse a previous agent's token. The Runtime owner alone admits and claims its input; use its existing identity, input phases and delivery lookup. The private route must share, not bypass, current Team delivery and Runtime admission/dispatch authorization. No second ledger.

### 5.1 Exact decision and effect boundaries

- Derive the settlement witness from the canonical Runtime record/provider observation for the exact binding, input ID, operation reference and terminal outcome. `admitted`, `claimed`, `consumed`, a Stop hook, UI idle, an empty stream or a log gap are not successful settlement. Non-success terminal outcomes go to the existing recovery/control owner. Do not equate provider turn generation with the Host binding generation unless the adapter proves that mapping.
- One stable decision/effect key per current member, original goal revision and authoritative trigger (terminal input/operation or new work/wait event with stable revision); retries keep the immutable original key and payload. Never derive keys from current time, report tokens or polling count. Retain consumed trigger witness under the existing retention rules; if the old witness has been pruned and cannot be recovered, hold rather than infer it is new. Coalesce all reasons for the same eligible next turn into one admitted input, not a separate turn per reason.
- Under the existing owner fence, persist intent/reservation before an effect, with one unresolved automatic intent per member/runtime authority. Revalidate current work, policy, grant, control revision, approval, runtime readiness/custody and budget before admission **and** the actual submit claim. Re-read existing queued user/peer/task messages: if one already supplies the required next turn, let it run and reconcile its actual outcome; do not insert a duplicate nudge. Preserve existing queue ordering and manual-input semantics; do not let a stale queued nudge start after user control or reassignment.
- The linearization point for "new work starts" is the existing durable Runtime claim; once accepted Stop/pause closes the corresponding admission fence, no later automatic claim may succeed. A claim ordered before closure can still be in physical handoff; use the original cancel/stop/cleanup contract, report unknown custody honestly, and never pretend it was not sent. Cover both not-yet-admitted and already-admitted unsent inputs. Member Stop must not be bypassed by lead reassignment or a different automatic producer; only authorized user Resume can clear its latch. Team Stop closes all automatic admission for that scope. Do not block user Stop on a model response or external wait.
- Normal continuation, board/review wake, watchdog recovery and runtime error recovery must coordinate on the same canonical admission/intent boundary for an opted-in member. Read-only status must never allocate an intent. Existing trusted human/peer messages continue through their real paths. A failed automatic wake cannot fall back to generic text delivery or a different runtime/member.

Read [RuntimeOwner](../../packages/legacy-agent-host/src/runtime/RuntimeOwner.ts), especially `admitDelivery`, `lookupDelivery`, `cancelDelivery`, `dispatchNext`; `consumed` denotes native submit acceptance, not success. Preserve its durable claim and no-replay-on-unknown semantics, current immutable fingerprints, and bounded queue. If the current policy cannot close the actual claim race, slice A remains a qualification blocker for automatic activation, not permission to bypass it.

## 6. Progress, retry and resource budget

Separate productive next turns from failure/no-progress recovery. Keep the existing two-attempt default for no-progress recovery unless evidence justifies a change. Real monotonic progress can permit many productive turns inside the objective's overall resource bounds. Avoid resetting all member budgets because one task moved, clock changed, status was reread, or another agent was active.

Use compact, task-bound evidence: genuine task/review cycle transition, resolved dependency, newly accepted artifact/check result tied to current revision, or verified operation result. Use the existing task-change/evidence owner (or a narrow adapter to its existing event IDs) where possible. Repeated comments/reports, timestamp churn, toggling pending/in_progress, rewriting the same artifact, repeating the same failing check, arbitrary tool invocation, model claim or successful input delivery do not replenish recovery. An observed transition or new evidence ID must be relevant, current and not previously consumed for that work key. Within the same long in_progress interval, a new verified substep can count; do not require artificial task-status changes or new commits for non-code work. If progress cannot be proved by available instrumentation, allow only the existing bounded no-progress attempts and explain the observation gap; do not add semantic transcript scoring. Track progress at the existing task/assignee/review-cycle episode, not one team-wide reset. A different member finishing a task cannot replenish the stuck member's attempts. Neither clock rollback nor restart opens a fresh recovery budget.

Use a simple distinction: ordinary next turn after proven progress (does not debit the lack-of-progress recovery allowance); bounded recovery turn after no verifiable progress (debits it exactly once); due observation of a registered expected wait (counts toward shared run bound, not a fabricated stall). The first planning/pickup turn is ordinary only once per fresh obligation; a model cannot gain fresh allowances by issuing new report tokens or manufacturing equivalent tasks. Prefer actionable dependencies and oldest eligible work within existing member/task priority; do not continually wake the lead while its children run. If one item exhausts its recovery budget, mark that item attention and let independent eligible items progress. A lead may choose a genuinely different in-scope resolution (e.g. correct a dependency or reassign through existing authority), but not cycle owners endlessly to reset the shared budget.

Reuse existing per-member rate limits and cooldowns for recovery; separate ordinary progress from recovery and do not globally increase nudge frequency. Apply a finite elapsed objective duration and total admitted automatic-turn bound shared by lead and members. Proposed initial opt-in presets: 12 hours and 100 automatic turns, editable before starting or by an explicit authorized extension (validate with canary; not a released default). Time includes waits; expiry is a budget disposition, not a failed CI/dependency. Manual turns and initial user input remain subject to existing provider permissions; they cannot replenish automatic limits. The bound is on automatic admissions, not token count or dollars. If trustworthy metering exists, show actual usage and unknown usage separately; do not invent hard currency/token accounting. Reuse existing provider limits. Require atomic Team-owner reservation against remaining shared budget before the delivery effect, linked to the original continuation intent. Reconcile a reservation after a crash by that same ID; release only with proven no-start/no-effect according to the existing owner contract, conservatively retain debit on unknown. Never count a transport retry as a fresh admission. Preserve control/settlement capacity even at zero budget. Do not add a distributed budget service. Exhaustion prevents further automatic admissions; show deadline, remaining turns, and affected work, allow explicit extension/resume, and keep original receipts. No automatic deadline renewal or cost escalation.

The next-turn message should be compact: goal/task reference, actionable reason, only necessary changed evidence or wait reference, and current required action. Reuse context/session and existing MCP pagination; no entire task board, conversation, diff or transcript on every wake. Keep original details accessible through existing read tools; never truncate acceptance evidence/errors to make a false pass. Observations, timer ticks and UI reads do not invoke the model.

## 7. Waiting and wakeup

Reuse real task dependencies, review state, clarification state and runtime busy/retry metadata. For an external operation not covered by them, retain a narrow task/goal-bound expected-wait record: kind, original task/goal revision, stable external reference (required for external waits), designated owner, reason, last observation, next check time and bounded horizon. For CI, use an exact repository/run ID plus expected commit/revision; old successful checks for another revision do not satisfy the wait. Reuse an existing structured MCP report path if it can express this under the current goal-bound authority; otherwise extend one existing Work Sync report contract with an optional validated wait payload (no standalone wait service and no broad new MCP tool catalog). The agent's statement is a wait request, not proof of external completion. Persist under the existing status/Team owner before acknowledging; if persistence fails, the wait is not registered. An untrusted/unknown external reference is a visible uncertain condition, not a permit to suppress work indefinitely. Cancel/supersede the waiting obligation on Stop/scope edit/reassignment; do not cancel the external operation unless independently authorized. Keep pending physical effect/receipt debt even after wait retirement.

For a task waiting on another member, rely on canonical dependency/review state and events. One designated owner observes an external operation; other affected work uses the existing dependency rather than launching identical checks. Distinguish a valid pending dependency from missing/deleted/cyclic dependencies and unresolved approval. Reuse board validation; if a remaining graph can deadlock, use a bounded detection of the actual missing/cyclic prerequisite and surface it to the lead, not a generic orchestration DAG.

Prefer existing trusted completion signals; otherwise a bounded scheduled recheck using authorized existing tools and backoff. No general webhook service, remote API polling engine or new credentials. A running tool stays busy; do not start another turn just to ask about it. If no reliable observer exists but the owner has an exact reference and authorized check tool, a due continuation may perform one read-only check and register the next due observation. Use the existing scheduler with proposed bounded backoff (5, 15, then at most every 30 minutes, respecting provider Retry-After and objective horizon); never poll an LLM while a trusted event/source is sufficient. If no supported tool or trustworthy reference exists, expose the capability gap and do not repeatedly guess. Waiting for human input has no automatic model-poll loop; wake on the actual reply/approval. Independent work continues. A queued/running CI job is expected wait, not failure. Distinguish failed checks, cancelled jobs and actual human approval from a pending job. Continue independent work. Do not restart CI or repeat an external mutation simply because a check is pending. 

## 8. Recovery, cancellation and compatibility

Use the Stage 1 identity and receipt boundaries (Team, project, run, member, runtime instance/generation, input, authority revision). Stop/revoke atomically closes further admission; cancel unsent intents and keep unknown/consumed outcomes held until reconciliation. Already running work follows existing stop/custody contract. Retry original logical commands only when current owner can prove the allowed outcome; no blind restart or replay of an external action. Restart and resume retain objective, limits, receipts and wait state only under supported current owner/explicit user resume; a fresh relaunch is not a continuation of an old objective. Normal Quit follows #982's existing custody/cleanup contract; no hidden daemon, automatic reopening of a sealed session or claim that closing the app keeps agents working. After crash, read/reconcile retained intent and physical custody first; restore observation even when new execution is held. If automatic reconnection is not supported by a tuple, display recoverable attention and require explicit Resume rather than fake continuity. OS sleep cannot execute work; after waking, coalesce due observations, preserve elapsed deadline and avoid a catch-up flood. Never fall back to an unrelated project or stale provider session.

An unavailable member or failed dependency must not freeze other members/teams. The inspected [Host wake composition](../../packages/legacy-agent-host/src/composition/createRuntimeWorkSyncWake.ts) loops over member entries and the coordinator pump also awaits settlement; the scheduler already has per-team retained dispatch/timeout support, so do not introduce another global loop. Prove isolation of A vs B both within one team and across teams. If a member callback can block a sweep, adapt the existing bounded scheduler/pump to per-member single-flight work with bounded admission/fairness and retained physical settlement. Logical timeout does not release the original writer fence; no repeated replacement promises, no unbounded fan-out and no dropping original outcomes. A genuinely team-owned mutation may serialize members of that team until its canonical fence resolves; do not bypass it to fabricate isolation. Independent teams remain serviceable; surface the affected member/team and cause. Use existing recovery queue and strict read/error semantics. An unknown snapshot is not empty or idle. Observe/repair original debt even when new automatic admission is disabled. No automatic retry for permission denial, invalid configuration, unsupported capability or user Stop; attention must retain specific reason.

Qualify only supported current Stage 1 provider/mode tuples. Check actual Claude, Codex and OpenCode V1 support; do not promise capabilities merely from a version flag. Unsupported tuple: show explicit capability reason and preserve existing manual/legacy behavior, no unsafe fallback. On rollback turn off new admission but preserve state/receipt read and settlement; never remove a durable record while work or effects may be outstanding.
