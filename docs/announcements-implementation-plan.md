# Новости и анонсы: план реализации

Статус: реализовано локально, выпуск не выполнялся. Дата: 2026-09-04. Результаты проверки: [announcements-verification.md](announcements-verification.md).

## 1. Цель и принятый scope

Добавить глобальное окно новостей в desktop-приложение. Автор публикует Markdown и изображения через Git, приложение читает статические файлы с сайта. Собственный backend, аккаунты и серверное хранение пользовательских отметок не нужны.

После одного обновления приложения новые публикации не требуют его перевыпуска. Автоматический показ работает на любом рабочем экране, включая редактор, но уступает активным диалогам и запросам подтверждения. Отдельная кнопка «Новости» позволяет вручную читать опубликованные материалы.

| Решение             | Контракт                                                                                        |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| Источник            | HTTPS на agentteams.live, публикация вместе с существующим лендингом                            |
| Срок актуальности   | validUntil либо publishedAt + 14 суток                                                          |
| Новые пользователи  | showToNewUsers = true по умолчанию                                                              |
| Задержка            | minUsageMinutes = 30 по умолчанию, суммарно между запусками                                     |
| Время использования | Открыто хотя бы одно основное окно; свёрнутое учитывается; сон и отсутствие окон не учитываются |
| Несколько новостей  | Автоматически только самая свежая подходящая; старые не появляются цепочкой                     |
| Повторный показ     | Закрытый/обработанный ID автоматически больше не появляется                                     |
| Правка текста       | Прежний ID обновляет содержимое в истории, но не создаёт новый автопоказ                        |
| Персональные данные | Время и отметки остаются в локальном профиле, в feed-запрос не передаются                       |
| Ручная история      | Доступна сразу, независимо от 30 минут, cohort и срока автоматического показа                   |

Не включать в эту поставку CMS, push при закрытом приложении, аналитику просмотров, синхронизацию устройств, персональный таргетинг, собственную систему подписи контента, произвольный HTML/JS и поддержку desktop-поведения в standalone/browser mode.

- Глобальная точка UI: [App.tsx](../src/renderer/App.tsx), рядом с ConfirmDialog и ToolApprovalSheet. Splash закрывается асинхронно: факт загрузки renderer ещё не означает готовность UI.
- Есть общие [Dialog](../src/renderer/components/ui/dialog.tsx), [AlertDialog](../src/renderer/components/ui/alert-dialog.tsx), [Markdown-компоненты](../src/renderer/components/chat/markdownComponents.tsx) и GFM. Общий [sanitize-профиль](../src/renderer/utils/markdownPlugins.ts) разрешает task/team/mention-протоколы и не подходит удалённым анонсам без ограничения.
- Готовый MarkdownViewer связан с локальными файлами, командами навигации, задачами и командами агентов. Переиспользовать оформление и безопасные элементы, не весь viewer.

- [API adapter](../src/renderer/api/index.ts) поддерживает Electron и HTTP fallback. Новый desktop-only контракт должен иметь явную capability и безопасное отсутствие поддержки в HTTP-режиме.
- [Лендинг](../landing/README.md) описывает Render Static Sites. Однако [.github/workflows/landing.yml](../.github/workflows/landing.yml) отдельно публикует GitHub Pages и использует другие команды/base URL. Нельзя считать этот workflow доказательством продакшен-деплоя Render.
- Read-only запрос к agentteams.live 2026-09-04 вернул HTTP 200, заголовок rndr-id и кеширование s-maxage=300. Это согласуется с Render за CDN, но настройки сервиса и build command ещё надо проверить перед интеграцией публикации.
- Готового lifetime-счётчика и глобального single-instance lock в проверенном коде не найдено. Последний пункт важен для двух экземпляров приложения с одним userData.

## 3. Формат публикаций и работа автора

### 3.1. Авторские файлы и выдаваемые файлы

Хранить авторский контент в Git, отдельно от генерируемой выдачи:

```text
landing/content/announcements/
  feed.config.json
  token-launch/
    meta.json
    body.md
    assets/banner.webp

landing/public/announcements/       # генерируется перед сборкой
  feed.v1.json
  content/token-launch/<bundle-hash>/body.md
  content/token-launch/<bundle-hash>/assets/banner.webp
```

Автор пишет обычный Markdown; метаданные лежат в небольшом JSON. Это не требует новой YAML/frontmatter-зависимости. Сборщик создаёт feed, проставляет значения по умолчанию, вычисляет хеши и копирует файлы. Генерируемая выдача не является вторым редактируемым источником истины.

Пример meta.json; поля optional можно опустить:

```json
{
  "id": "token-launch",
  "title": "Новости проекта",
  "publishedAt": "2026-09-15T12:00:00Z",
  "status": "published",
  "showToNewUsers": true,
  "minUsageMinutes": 30
}
```

### 3.2. Точный контракт

- id: стабильный lowercase slug по шаблону [a-z0-9][a-z0-9-]{0,79}, уникальный во всём каталоге и совпадающий с именем папки. Не переиспользовать для другого события. Идентификаторы хранить в Set/Map, не в небезопасном object dictionary.
- title: обычный текст, 1-200 символов после trim; не HTML.
- publishedAt: обязательная корректная ISO 8601 дата с timezone; нормализовать в UTC. Это дата начала доступности, а не время сборки.
- validUntil: optional; строго больше publishedAt. Отсутствие означает +14 × 24 часа. null, пустая строка и неверная дата являются ошибкой, а не запросом default.
- showToNewUsers: optional boolean, default true. После первой публикации не менять: для другого cohort-смысла нужен новый ID.
- minUsageMinutes: optional конечное неотрицательное целое число минут; default 30. Ноль явно отключает задержку. Не применять default через truthy-проверку. Перевод в миллисекунды обязан укладываться в safe integer.
- status: draft / published / archived / withdrawn. Draft и withdrawn не попадают в публичную выдачу. Archived виден в ручной истории, но не показывается автоматически.
- id и publishedAt неизменяемы после первой публикации. Обычная правка body/title/validUntil/minUsageMinutes не обходит ID-дедупликацию.
- Истёкшие published-материалы остаются в истории с пометкой об окончании актуальности. Future-материалы до publishedAt в UI не видны.

Feed v1 содержит schemaVersion, revision, autoShowEnabled и массив нормализованных записей. Запись содержит URL/путь body и bodySha256. revision вычисляется из канонического содержимого, а не случайного значения или текущего времени; повторная сборка тех же исходников даёт тот же результат. Неизвестные дополнительные поля v1 игнорируются; неверный тип известного поля или неизвестная schemaVersion отклоняет всю ленту для авто, без частичного выбора старых записей. Новое обязательное условие показа, которое старые клиенты не умеют соблюдать, требует новой schema, а не молча игнорируемого поля v1.

bundle-hash зависит от body и всех локальных assets, включая их пути. Изменение картинки создаёт новый URL bundle даже при неизменном Markdown. bodySha256 относится к фактически отдаваемым UTF-8 bytes; не менять переносы строк после вычисления хеша. Контрольная сумма защищает от смешения версий кеша, не является криптографической подписью издателя.

Предлагаемые технические границы v1: feed до 512 KiB и 1000 записей, один body до 256 KiB, одно изображение в исходниках до 5 MiB. Превышение даёт понятную build-ошибку, а не незаметное усечение. Перед достижением лимита каталога можно отдельно добавить пагинацию истории.

### 3.3. Проверка публикации

Сборщик проверяет schema/types, уникальность ID, даты, допустимые пути, наличие body/assets, пределы размера, переносимость имён на Windows/macOS и отсутствие symlink/path traversal. Генератор заменяет только собственный announcements output, не весь landing/public. Валидатор относительно Git base запрещает удаление уже опубликованных метаданных, изменение нормализованных immutable-полей и повторное использование ID; для отзыва использовать withdrawn, для истории archived. Черновики допускают правку всех полей.

Валидация и генерация должны выполняться до любого production build лендинга, включая реальный Render build command. Только зелёного GitHub workflow недостаточно, если Render независимо запускает сборку. Проверка immutable-полей выполняется обязательным content-check job на PR и deploy-ветке с доступным Git base; отсутствие base не означает успех. Для Render включить After CI Checks Pass и убедиться, что этот job действительно запускается на изменениях контента и валидатора, без skipped/neutral success. Структурная проверка и генерация всё равно выполняются в самом build. Это использует имеющиеся CI и механизм Render, без отдельного deploy orchestrator.

Контент, закоммиченный в публичный Git, публичен даже при draft/future/withdrawn. Дата будущего показа не обеспечивает секретность запуска.

## 4. Кто считается новым пользователем

У свежего локального профиля сохранить firstAppOpenedAt один раз при первом основном окне. Для конкретной публикации:

```text
newForAnnouncement = firstAppOpenedAt >= publishedAt
cohortAllowed = showToNewUsers || !newForAnnouncement
```

Пользователь, начавший пользоваться после публикации с showToNewUsers=false, не получает её автоматически ни через 30 минут, ни через неделю. Это ограничение cohort, а не временная задержка. Публикации после его первого запуска рассматриваются как новости для существующего пользователя.

minUsageMinutes применяется отдельно ко всем профилям: нужен соответствующий объём накопленного времени. Обычно у давних пользователей порог уже пройден; высокий индивидуальный порог может отложить конкретное объявление и для них.

### Миграция при первом выпуске функции

Реальное время и точную дату старых запусков восстановить нельзя. Не использовать даты файлов проектов, установки provider/runtime или модификации конфигурации как точные часы использования.

- Новый профиль: origin=fresh, firstAppOpenedAt=фактическое первое открытие окна, accumulatedOpenMs=0.
- Достоверно ранее существовавший профиль: origin=legacy, firstAppOpenedAt=null, trackingStartedAt=сейчас, accumulatedOpenMs=0. Старые 30 минут не придумывать; первый порог накопится после обновления.
- Для legacy публикации после trackingStartedAt точно относятся к существующему пользователю. Для более ранних объявлений с showToNewUsers=false автоматически не показывать: неизвестно, пользовался ли человек приложением до публикации. showToNewUsers=true разрешает показ после порога.
- При неоднозначном распознавании использовать ту же консервативную unknown-политику. Наличие любых файлов Chromium, созданных текущим запуском, не является доказательством старого профиля.
- Сигнал существующего профиля фиксировать до инициализации, способной создать/нормализовать его файлы. Определить и протестировать минимальные app-owned признаки; не сканировать пользовательские проекты и историю сессий.
- Если достоверного признака свежести нет, не блокировать релиз: origin=unknown безопасно использует правила legacy. Ограничение должно быть явно отражено в диагностике и тесте миграции.

Точка интеграции: отдельный ранний bootstrap helper после bootstrapUserDataMigration, до sentryBootstrap и eager ConfigManager. Использовать resolved userData и исходный snapshot признаков, переданный в composition. Синтетический current-path-exists при dev override не доказывает старую установку. Достаточно ограниченных app-owned marker/config checks; список подтверждённых признаков зафиксировать тестами, при неопределённости выбирать unknown.

## 5. Выбор новости и отсутствие очереди старых поп-апов

Порядок задаёт пара orderKey=(publishedAt в UTC, id). При одинаковой дате ID сравниваются стабильным бинарным/лексикографическим сравнением, не localeCompare. Позиция записи в JSON не имеет значения.

Локально хранить autoSuppressedThrough: максимальную границу новостей, которые больше не следует предлагать автоматически, плюс handledIds и dismissedIds. Это разные причины: обработанная новость могла не отрисоваться из-за crash/race; закрытая была явно закрыта пользователем. Не выдавать эти состояния за доказанный просмотр.

Алгоритм автоматического выбора:

1. Дождаться загрузки локального состояния и валидной свежей ленты.
2. Проверить autoShowEnabled, desktop capability, готовность UI и право экземпляра на запись состояния.
3. Оставить published, для которых publishedAt <= now < validUntil, cohort разрешён, usage >= порога, ID отсутствует в handled/dismissed, orderKey > autoSuppressedThrough.
4. Выбрать максимум orderKey среди подходящих записей.
5. Скачать и проверить body. Если body именно этой новости недоступен, не подставлять более старую в качестве fallback.
6. Перед показом повторно проверить feed revision, ID/body hash, срок, usage, focus и overlay readiness. Затем выполнить атомарное потребление, описанное ниже.

Важные примеры:

| Ситуация                                               | Результат                                                   |
| ------------------------------------------------------ | ----------------------------------------------------------- |
| У нового профиля 10 свежих записей и 0 минут           | Ничего автоматически; ручная история доступна               |
| Накопилось 30 минут, все 10 подходят                   | Один поп-ап самой свежей                                    |
| Его закрыли и перезапустили приложение                 | Предыдущие 9 не всплывают                                   |
| Появилась действительно новая подходящая публикация    | Она может показаться                                        |
| Более новая требует 60 минут, старая 30                | В 30 можно показать старую; в 60 новую                      |
| Более старая требует 60, более новая уже показана в 30 | Старая остаётся только в истории                            |
| Самая новая ещё future                                 | Она не продвигает границу и не блокирует текущую подходящую |
| Исправлен текст прежнего ID                            | Обновляется история, новый автопоказ не возникает           |
| Истёк срок прямо во время загрузки                     | Перед показом отказаться, ничего не потреблять              |
| Самая свежая отозвана после закрытия                   | Граница не откатывается, старые не всплывают                |

Переоценка нужна при запуске, успешном refresh, достижении ближайшего usage-порога/даты публикации, возвращении окна на передний план и освобождении UI после временного blocker. Не ждать следующих 15 минут, если пользователь ровно сейчас достиг 30 минут.

Закрытие новости само по себе не вызывает выбор следующей. Новость, появившаяся во время чтения другой, остаётся до следующего независимого события проверки; текст открытого окна не заменять под пользователем.

## 6. Локальное состояние, транзакции и сбои

### 6.1. Хранилище

Маленький feature repository под устойчивым app userData/data/announcements; не хранить это в командных каталогах, конфигурации проекта или renderer localStorage. Это сохраняет независимость от навигации, SSH-контекста и React reload.

Состояние v1: schemaVersion, origin, firstAppOpenedAt, trackingStartedAt, accumulatedOpenMs, autoSuppressedThrough, handledIds, dismissedIds. У handled/dismissed/floor нет TTL; удаление публикации, истечение срока и очистка контентного кеша не очищают эти отметки. Отдельный одноразовый initialized marker позволяет отличить потерянное состояние функции от её первого включения.

Все изменения выполняет один writer: последовательная очередь read/modify/persist/publish. Checkpoint времени не может перезаписать более свежий dismiss старой копией JSON. Использовать подтверждаемую atomicWriteAsync с strict durability и syncDirectory, не fire-and-forget ConfigManager.

Первичная инициализация: сначала долговечно записать state, затем marker. До успешного завершения обеих записей запрещены claim и manual consumption. Полная таблица восстановления:

| State                                     | Marker                                    | Действие                                                         |
| ----------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------- |
| Отсутствует с ENOENT                      | Отсутствует с ENOENT                      | Bootstrap под writer lock                                        |
| Валидный                                  | Отсутствует                               | Сохранить state, долговечно восстановить marker                  |
| Валидный                                  | Валидный                                  | Обычная работа                                                   |
| Отсутствует                               | Есть                                      | Fail closed, история обработанных публикаций могла быть потеряна |
| Повреждённый/нечитаемый/неизвестной схемы | Любой                                     | Fail closed, даже если marker отсутствует                        |
| Любой                                     | Повреждённый/нечитаемый/неизвестной схемы | Fail closed                                                      |

EACCES/EIO не являются отсутствием файла. В fail-closed режиме не сбрасывать историю в пустую, сохранить проблемный файл, отключить авто и оставить ручное чтение с диагностируемой ошибкой. Не восстанавливать старую резервную копию так, чтобы она возвращала уже обработанные объявления.

При обычном обновлении приложения, миграции userData или смене брендинга сохранять этот каталог. Удаление всего профиля/другой компьютер означает новое локальное состояние; глобальной гарантии «один раз на человека» без аккаунта нет.

### 6.2. Автоматическое потребление до отображения

Сначала подготовить проверенный body и готовый UI. Затем в одной операции:

```text
claimAuto(expectedRevision, expectedCandidateId):
  повторно выбрать и проверить кандидата
  persist handledIds += candidate.id
          autoSuppressedThrough = max(previous, candidate.orderKey)
  только после успешной записи вернуть одноразовое разрешение на показ
```

Запись выполняется до возврата разрешения. Renderer не может запросить произвольный URL, изменить usage/дату первого запуска или самостоятельно назначить кандидата. Повторный вызов/React StrictMode не выдаёт второй автопоказ. Показ привязан к конкретному разрешённому webContents и поколению UI.

Закрытие через X/Escape/backdrop/кнопку подтверждения идемпотентно добавляет ID в dismissedIds. Закрыть окно можно сразу, не удерживая пользователя на ошибке диска: durable handledIds/floor уже защищают от повторного автоматического появления. Ошибку дополнительной записи сохранить в диагностике, повторить ограниченно; не утверждать, что запись успешна.

**Принятый компромисс:** crash между успешным claim и paint может лишить новость одного автопоказа. Она остаётся доступна вручную. Это осознанный выбор в пользу отсутствия повторов; не обещать одновременно идеальную доставку и exactly-once UI при авариях.

Если durable claim не удался или исход записи неизвестен, окно автоматически не открывать. Перечитать состояние; при сохраняющейся неопределённости отключить авто до восстановления repository. Нельзя «для удобства» открыть без записи и потом повторять при каждом запуске.

### 6.3. Несколько экземпляров приложения

Несколько окон одного Electron process используют один tracker, без умножения минут. Два процесса с одним профилем требуют отдельной защиты: process-local очередь этого не решает.

Для MVP использовать один feature writer-owner на профиль. Во втором экземпляре показ статей и автоматических окон временно недоступен: UI сообщает, что новости доступны в уже запущенном приложении. Это узкое исключение из доступности истории, которое сохраняет гарантию «закрыл и больше не показывать» без межпроцессного командного транспорта. Read-only чтение статьи без записи отметки не предлагать: иначе владелец может позже показать её снова. Остальное приложение второго экземпляра работает нормально.

Владелец освобождает право после flush, когда не осталось основных окон, или при завершении; следующий экземпляр с окном пробует забрать его по событию foreground/open и редкому bounded-frequency retry, например раз в 30 секунд. При handoff допустимо консервативно не засчитать короткий промежуток, но нельзя удвоить минуты. При двух процессах одновременно учитывается время окон owner-процесса; полноценный межпроцессный учёт всех окон не входит в MVP.

Не добавлять глобальную single-instance политику для всего приложения. Нужен узкий file-owner lock с owner token/PID и identity-fenced release/recovery. В проекте есть подходящий образец durable-операций в TeamPermanentDeletionLock; не подтягивать его доменную службу целиком. Обычный withFileLock нельзя бездумно держать постоянно: его age timeout способен отнять lock у живого процесса, а unlink не ограждён identity.

Lock живого/неопределённого владельца не красть по времени. Мёртвый владелец удаляется только после проверки identity; PID reuse/EPERM трактовать консервативно. Сетевые запросы при передаче владения отменяются, поколение service меняется, старые callback не записывают состояние. Второй процесс не начинает независимый счётчик в обход busy-lock.

Порядок получения права: acquire lock → перечитать authoritative state/marker с диска → validate/init/repair → новое service generation → tracking/claims. Нельзя продолжать с кешированной копией бывшего secondary. Перед release запретить новые mutations, закрыть интервал, отменить fetch, дождаться очереди и flush; release делает только текущий owner с проверкой identity. Неопределённая запись оставляет service fail-closed; ошибка блокировки writer_busy сама по себе не означает повреждение repository.

## 7. Накопление времени

Tracker живёт в main feature application, чистая математика интервалов в core. Renderer не отправляет число накопленных секунд. Считать только зарегистрированные основные окна приложения: DevTools, auth/browser helper и служебные окна не подходят.

В текущем main createWindow вызывается раньше initializeServices. Ранний window-lifecycle helper должен сохранить первое show/default-show и список основных окон; после создания feature передать snapshot и подписать дальнейшие события. Не терять стартовые минуты и не обнаруживать окна через неотфильтрованный BrowserWindow.getAllWindows. Завершение учитывать по closed, не по отменяемому close. Dispose подключить к принятому shutdownServices, не к первой попытке before-quit.

- Окно ещё скрыто до первого показа: время не идёт. После первого показа свёрнутое окно учитывается; скрытие приложения при живом основном окне не обнуляет сессию.
- Окна нет, но process остался в macOS dock/tray: время не идёт.
- Потеря focus не останавливает время, но блокирует новый автоматический поп-ап.
- На suspend закрыть текущий интервал; на resume начать новый без начисления сна. Не использовать один Date.now() - startedAt на весь запуск.
- Для длительности использовать monotonic clock и явные границы жизненного цикла. Накопленные сохранённые миллисекунды не зависят от смены timezone или перевода настенных часов.
- Небольшой heartbeat, например 5 секунд, поддерживает актуальный in-memory total; checkpoint на диск каждые 30 секунд и на закрытие последнего окна/suspend/штатное завершение.
- Если heartbeat вернулся после большого необъяснённого разрыва, например больше 15 секунд при 5-секундном tick, консервативно исключить весь этот интервал и сбросить anchor. Это защищает от пропущенного sleep event ценой возможного недосчёта при долгой блокировке main. Явный suspend сразу закрывает интервал; resume всегда создаёт новый anchor.
- На resume/dropout заново оценить условия, но не открывать окно в фоне. Повторные suspend/resume и несколько window events должны быть идемпотентны.
- Flush участвует в существующем quit lifecycle, не создаёт второй конкурирующий preventDefault/quit loop. При отменённом quit tracker продолжает работать, не удваивая уже начисленное.
- Системное завершение на Windows может не вызвать обычные quit events: гарантировать периодические checkpoints, не полагаться только на shutdown handler.
- При crash теряется лишь несохранённое время при исправном диске; при I/O failure или долгом main stall недосчёт может быть больше 30 секунд. Не обещать абсолютную точность таймера.

Проверить работу monotonic clock и power events на закреплённой проектом Electron-версии, а не только по latest docs. Это таймер условий показа, не бухгалтерский учёт и не система аналитики активности.

## 8. Загрузка, кеширование, время публикации и отзыв

### Сетевой слой

- main получает только фиксированный origin/path feed. URL не приходит из renderer или проекта. Запросы анонимные, без app/provider credentials, cookies и идентификатора установки. Development/test endpoint разрешён только через явную dev/test composition; production-путь нельзя перенастроить произвольным IPC.
- Fetch при старте после локальной инициализации; затем раз в 15 минут с небольшим jitter. На возврате сети/foreground/resume обновлять, если данные устарели; объединять одновременные запросы и ограничить частые повторы.
- HTTPS, нормальная проверка сертификата, redirect только внутри доверенного origin и ожидаемого namespace. Credentials, нестандартные порты, protocol-relative URL, file/data/localhost/private network назначения недопустимы.
- Timeout около 10 секунд, потоковый лимит decoded bytes, проверка схемы и типа ответа. HTML с HTTP 200 от SPA fallback не является валидным feed/Markdown.
- Ограниченные retry только для временной сети/5xx/429 с ограниченным Retry-After; не повторять каждый render и не перепроверять бесконечно испорченный JSON. Ошибка не влияет на работу основного приложения.
- На body 404/hash mismatch один принудительный refresh feed, затем остановка до обычной следующей проверки. Старую публикацию вместо сломанной свежей не показывать.

### Кеш и свежесть

- Manifest с ETag/If-None-Match; ответ 304 пригоден только при наличии соответствующего валидного кеша. После рестарта загружать ETag вместе с body feed, не отдельно.
- Запись нового feed только после полной валидации. Некорректный ответ не заменяет последнюю хорошую копию и не обновляет время её свежести.
- Для MVP автопоказ разрешён после успешного refresh в текущем запуске, пока validation age не больше 20 минут. После network error, suspend или подозрительного скачка часов авто приостановить до успешного refresh. Это намеренно консервативнее использования вчерашней ленты.
- Offline: доступны ранее загруженные body в ручной истории с пометкой устаревшего состояния; новые автоматические окна не открываются. Изображения могут отсутствовать без отдельного медиакеша, показывать fallback.
- Body кешируется по id+bodySha256; разумный LRU, например 20 документов/5 MiB. Вытеснение кеша не удаляет dismissedIds, handledIds или floor.
- Даты публикации/истечения проверять повторно перед claim и при открытии истории. Граница expires строгая: now == validUntil уже не eligible для авто; в истории это пометка, не запрет чтения. Планировщик не полагается на один длинный setTimeout, который мог пропустить sleep; ближайший wake ограничен коротким интервалом, без overflow таймера на очень большом minUsageMinutes.
- Календарные ограничения используют Clock port. Корректность абсолютных дат зависит от часов устройства; при обнаруженном существенном скачке приостановить авто до refresh, не менять накопленную длительность. Без доверенного серверного времени нельзя обещать защиту от намеренно неверной даты на устройстве.

### Хостинг и отзыв

- feed: Cache-Control с обязательной revalidation/коротким shared-cache TTL, ETag; целевой CDN TTL не больше 60 секунд. Проверить реальные headers на опубликованном URL. Nuxt routeRules не считать достаточной настройкой Render Static Site headers.
- content с bundle-hash: длительное immutable caching. Относительные ссылки body разрешаются относительно его опубликованного bundle URL.
- Отдавать существующие JSON/MD напрямую; неизвестный путь внутри announcements должен давать 404, а не главную страницу сайта.
- autoShowEnabled=false прекращает новые автопоказы после получения новой ленты. Уже прочитанные IDs/floor не удаляются; включение обратно не повторяет старые окна.
- withdrawn удаляет материал из выдачи. После успешного refresh убрать его из доступной истории/очереди и локального кеша. Если он открыт, закрыть с нейтральным сообщением об отзыве, не запуская следующий поп-ап.
- Kill switch не является мгновенным push: задержка включает polling, deploy и CDN; у полностью offline клиента нет свежего знания об отзыве. Это ограничение показывается в runbook.

## 9. UI, Markdown и модальные окна

### Глобальный host

Один AnnouncementHost в корне приложения через публичный renderer entrypoint feature. Он не привязан к активной команде, проекту, вкладке или SSH-контексту. Автоматическое окно открывается только в видимом focused основном окне после splash/onboarding readiness и без блокирующих поверхностей; не поднимать/активировать приложение средствами OS.

У host явные режимы idle / auto / history. Автоматический prepare/claim допускается только в idle. Refresh и usage threshold во время ручного чтения обновляют данные, но не потребляют и не открывают другой материал поверх истории. Закрытие auto/history само по себе не является независимым trigger нового выбора; освобождение стороннего временного blocker является.

Использовать shared Radix Dialog, локализованные элементы управления, корректный accessible title, клавиатуру/Escape, возвращение focus, ограничение высоты с прокруткой и адаптивную ширину. Большие таблицы/код прокручиваются внутри контента и не растягивают всё окно. Проверить light/dark theme и небольшой desktop viewport.

UI-строки добавить через существующую localization feature и проверить pnpm i18n:validate. Сам текст анонса показывается на языке, на котором написал автор; автоматический перевод и несколько локализованных body на ID не входят в v1.

### Арбитраж с другими окнами

Нужен маленький shared overlay-occupancy контракт, не новая универсальная система управления окнами. Общие Dialog и AlertDialog регистрируют фактически открытый blocking content. Важно: wrapper DialogContent может оставаться React-mounted при закрытом Radix Root; marker размещать внутри реально открытого Content либо связывать с controlled open. Учитывать forceMount и exit animation, StrictMode cleanup.

Явно подключить legacy blockers: UpdateDialog, ConfirmDialog, TerminalModal, ToolApprovalSheet, CommandPalette, QuickOpenDialog, GoToLineDialog, ContextSwitchOverlay и app onboarding. Не сканировать DOM по role=dialog: часть этих поверхностей имеет другой role или не имеет его.

ProjectEditorOverlay является полноценным рабочим экраном и не блокирует новости всё время своего существования. Его временные QuickOpen/GoToLine блокируют. Announcement и его собственная history surface не должны блокировать сами себя.

Перед paint renderer повторно сверяет focus и поколение registry. Если после durable claim открылся более важный диалог, новость уступает ему; обработанное состояние не откатывается. Приоритетный dialog, открывающийся во время чтения новости, также получает фокус, без автоматического повторного открытия вытесненной новости.

### Markdown-профиль

- Поддержать GFM: заголовки, таблицы, списки/чекбоксы, цитаты, ссылки, изображения/GIF, code blocks и подсветку. Переиспользовать существующее оформление; не менять поведение Markdown в чатах и review.
- Для удалённых анонсов raw HTML выключен. Не исполнять MDX, JS, iframe, video embed, forms, style или обработчики событий. Это не ограничивает стандартный Markdown и GFM.
- Отдельный URL/sanitize профиль без task/team/mention/file/data/javascript протоколов. Переопределить a/img; не использовать FileLink/LocalImage и не передавать baseDir проекта.
- Относительные URL разрешать через URL parser относительно body URL, затем проверять итоговую схему/origin. Не путать их с локальными путями. Запретить credentials и protocol-relative обходы; проверять нормализованный, а не исходный строковый prefix.
- Ссылки наружу только HTTPS через существующий безопасный openExternal; не навигировать Electron renderer на сторонний сайт. Якоря внутри документа обрабатывать локально.
- Автозагрузка картинок только из namespace опубликованных assets на доверенном origin. В MVP внешнюю картинку надо положить рядом с Markdown. Ограничить отображение, loading=lazy, referrerPolicy=no-referrer, fallback по ошибке. Никакого чтения локальных файлов через IPC.
- Ограничить объём подсвечиваемого кода; для большого допустимого документа использовать лёгкий режим без highlight. Не добавлять native title tooltips; помощь через shared Tooltip.

### Ручная история

Кнопка «Новости» доступна из общего app navigation/menu на любом экране. Список сортируется тем же orderKey, содержит title/date и пометку истечения срока. История не фильтруется по cohort/usage; не возвращает future/draft/withdrawn записи. Список ограничен текущим опубликованным каталогом, не обещает вечный архив.

Открытие списка само по себе ничего не помечает прочитанным. Явное открытие статьи сначала загружает и проверяет body, затем применяет consumption-through её orderKey перед выдачей статьи UI. Ошибка загрузки не меняет floor/handled. Это не позволяет после ручного чтения свежей новости показать более старое объявление. На ошибке persistence у owner ручное чтение всё равно доступно, но автоматические окна этой сессии отключаются. При закрытии статьи записывается dismissedId; повторное ручное открытие возможно. Для writer_busy второго экземпляра действует отдельное ограничение §6.3, без открытия статьи и обещания сохранения отметки.

## 10. Размещение кода и контракты

Новая feature: src/features/announcements, с contracts, core/domain, core/application, main/composition, необходимыми main adapters/infrastructure, preload и renderer. Пустые папки ради шаблона не создавать.

- core/domain: нормализация metadata/state, orderKey, eligibility/cohort/expiry, выбор newest, переходы floor/handled/dismissed и арифметика интервалов.
- core/application: GetNewsSnapshot, Prepare/ClaimAutoAnnouncement, OpenManualAnnouncement, DismissAnnouncement; порты Clock, AnnouncementSource, AnnouncementStateRepository, ContentCache.
- main: HTTPS source, file repository/ownership, Electron lifecycle tracker, композиция и IPC input adapter. Все filesystem/network/Electron детали здесь.
- preload: узкий типизированный bridge; renderer: state projection, host, history и безопасный Markdown.
- Пример API: capabilities/getSnapshot/prepareAuto/claimAuto/openManual/dismiss/onStateChanged. Уточнить минимальную форму при реализации; payload не содержит произвольных путей, URL, счётчиков или raw HTML.
- IPC проверяет shape, ID, size, sender и owning window. Обновления содержат только необходимые UI DTO, без путей профиля, внутренних ошибок filesystem и лишних персональных данных.
- browser/HTTP fallback возвращает capability unavailable и не запускает tracking. Не создавать фиктивные per-user минуты, общие для всех browser clients одного сервера.
- Новые production файлы до 800 строк. Не увеличивать frozen legacy files и baseline. Для интеграции в большой main shell вынести минимальный связный блок существующего lifecycle/composition в helper, если текущие extension points не позволяют уложиться в ограничение; без широкого рефакторинга runtime.

У shared/types/api.ts сейчас исчерпан baseline 1158 строк: расширение ElectronAPI оформить через небольшое извлечение typing/API fragment, а не повышение лимита. У main/index.ts есть некоторый запас относительно baseline; не делать отдельное извлечение заранее, если добавление тонкого wiring укладывается в guard. Точки подключения: composition/IPC register-remove в main/index.ts, bridge в preload/index.ts, capability в HttpAPIClient; runtime-логика остаётся в feature.

## 11. Последовательность реализации и review budget

### Checkpoint 1: данные, время и публикация

1. Зафиксировать domain contract/defaults и fixtures, реализовать focused domain tests.
2. Реализовать source metadata validator и детерминированный generator, пустую production feed с autoShowEnabled=false; подключить его к фактическому build лендинга.
3. Реализовать repository, initialized marker, writer ownership и crash/error policies; проверить их только в disposable temp directories.
4. Подключить main tracker и миграцию. Он не показывает UI, не запускает агентов и не пишет в реальные проекты. В этой версии уже можно накапливать время.
5. Проверить production статические paths/headers только read-only запросами после отдельно выполненной публикации. В этом плане ничего не деплоится.

Checkpoint самостоятельно полезен: инфраструктура публикации готова, время начинает накапливаться, popup остаётся выключен. Не связывать его merge с готовностью всей UI-функции.

### Checkpoint 2: безопасный popup и история

1. Реализовать feed/body fetch, cache/freshness и main use cases с повторной проверкой перед claim.
2. Подключить contracts/preload и безопасную HTTP capability.
3. Реализовать глобальный host, history, Markdown-профиль и overlay arbitration.
4. Добавить focused integration/renderer tests и пройти изолированную Electron fixture-проверку.
5. Обновить runbook автора и диагностику; проверить пустую feed и disabled mode как штатные состояния.
6. Выпустить приложение с готовой функцией. Первый реальный анонс включается отдельным обычным изменением контента после проверки production URL.

Цель: два самостоятельных dependency-safe PR примерно до 2000 changed LOC каждый, включая код и tests; generated-артефакты считать отдельно. Если первый checkpoint выходит больше бюджета из-за coordinator/lifecycle, выделить отдельный связный persistence/usage PR до UI. Не разрезать транзакцию consume/claim между mergeable PR.

Уточнённый ориентир всего scope: 1500-2300 production/tooling LOC + 700-1100 test LOC. Предыдущие 800-1200 были грубой оценкой и не учитывали в полном объёме cross-process ownership, legacy modal arbitration и generator/publishing gates. Новые библиотеки не планируются; при реальной необходимости проверять актуальную стабильную версию перед добавлением.

## 13. Проверка реализации и изоляция

Во время реализации ориентироваться на следующие команды; сейчас они не запускались:

```sh
pnpm typecheck
pnpm lint:fast:files -- <затронутые TS/TSX файлы>
pnpm exec vitest run test/features/announcements
pnpm guard:source-file-size
```

Добавить generator/validator tests в предусмотренную команду CI; имена новых scripts зафиксировать при реализации. Для изменения shared Dialog/AlertDialog отдельно прогнать существующие focus/overlay тесты. При широком изменении границ выполнить pnpm lint. Выполнить штатные обязательные CI gates на финальном head каждого PR; не повторять доказанные тяжёлые проверки без нового риска.

UI проверять только через pnpm dev:mcp и renderer CDP на 9222. Обязательны обе существующие переменные: AGENT_TEAMS_ELECTRON_USER_DATA_DIR и AGENT_TEAMS_ELECTRON_CLAUDE_ROOT, каждая указывает на новую sandbox-папку. Один новый userData не изолирует реальный ~/.claude и ConfigManager. Fixtures не содержат пользовательских проектов. Network source/clock подменяются в dev/test composition, не скрытыми production IPC-командами; dev по умолчанию не показывает реальные production-анонсы. Проверить сохранение между двумя запусками именно этого sandbox.

Межпроцессные проверки выполняются только с временными state directories и собственными child processes. PID reuse/EPERM моделируются через port, без действий над реальными чужими PID. Если порт 9222 занят, не закрывать чужой процесс: выбрать поддерживаемый тестовый CDP port и подключиться к нему явно.

Не открывать Computer Use/native folder picker. Не создавать/запускать команды агентов, provisioning, task assignment или terminal runtime для проверки новостей. Не использовать реальный пользовательский профиль, существующие команды и проекты, включая claude-runtime. Cleanup только собственных fixture-процессов/папок.

Статику проверять локальным HTTP fixture и, после публикации, GET/HEAD публичных URL. Разработка новости не требует запуска browser-mode основного приложения или live provider smoke.

## 14. Наблюдаемость, откат и acceptance

Локальные структурированные reason codes: feed_invalid, fetch_failed, stale_cache, not_due, usage_pending, cohort_excluded, already_handled, suppressed_by_floor, overlay_busy, state_unavailable, writer_busy, claim_committed, withdrawn. Не логировать каждую heartbeat/фильтрацию; только существенные переходы и агрегированные ошибки. Не отправлять серверу usage, dismissed IDs, содержимое профиля или телеметрию просмотров.

В ручной истории можно показать состояние обновления и понятную ошибку загрузки. Автоматическая ошибка новостей не порождает другой модальный диалог и не блокирует работу пользователя.

Откат контента: autoShowEnabled=false или withdrawn, затем проверить фактическую раздачу feed. Откат кода: отдельный revert UI checkpoint; накопленное состояние не удалять. Старый клиент с неизвестной новой schema безопасно отключает авто. Возврат предыдущей версии feed не откатывает локальный floor и не повторяет обработанные ID.

Acceptance:

1. Реальная публикация нового Markdown с картинкой появляется в установленной версии без нового app release.
2. Новый профиль не видит автоматических новостей до своего порога; суммарные минуты сохраняются между запусками и не включают сон.
3. Из десяти подходящих объявлений автоматически открывается одно; закрытие, перезапуск, смена вкладки и редактирование body не запускают остальные.
4. Новая более поздняя подходящая публикация может показаться; showToNewUsers и validUntil выполняются на точных границах.
5. Все рабочие экраны поддержаны, приоритетные диалоги не перекрываются, фоновые окна не перехватывают focus.
6. Ручная история доступна сразу, в том числе для закрытых/истёкших материалов; недоступность сети/диска деградирует безопасно.
7. Удалённый Markdown не получает доступ к локальным файлам, внутренним task/team links, JS и произвольным IPC.
8. Сбой persistence не превращается в повторяющийся popup; несколько окон/экземпляров не удваивают время.
9. Есть воспроизводимое sandbox evidence для restart/power/focus/claim races и production evidence для статических headers/paths.

## 15. Источники и оставшиеся проверки перед кодом

- [Electron powerMonitor](https://www.electronjs.org/docs/latest/api/power-monitor): main-owned suspend/resume; проверить поведение на проектной версии и целевых ОС.
- [Electron app lifecycle](https://www.electronjs.org/docs/latest/api/app): quit может быть отменён; Windows shutdown не гарантирует обычные quit events.
- [Electron BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window): показать/закрыть/фокусировать окно следует различать при учёте и показе.
- [Nuxt public directory](https://nuxt.com/docs/3.x/directory-structure/public): файлы выдаются как static assets, не требуют backend.
- [Render Static Sites](https://render.com/docs/static-sites), [headers](https://render.com/docs/static-site-headers), [redirects](https://render.com/docs/redirects-rewrites), [deploys after CI checks](https://render.com/docs/deploys): проверить atomic publish, CDN headers, настоящий content-check и отсутствие SPA fallback для feed.

До реализации уточнить по фактическому коду только технические привязки: ранний profile-origin signal, расширение существующего quit lifecycle без роста frozen main файла, полный inventory blockers и реальный Render build command. Эти проверки не меняют принятый product contract и не требуют возвращать пользователю уже решённые вопросы.
