## 1. Обязательное поведение

Очередь доступна для ordinary text messages в 1on1, стандартном Group и каждом custom group. В custom group поддержаны все существующие selected recipients, включая All; directed group item остаётся group post и никогда не становится DM.

- Cmd+Enter на macOS, Ctrl+Enter на Windows/Linux добавляет текущий текст в очередь. Обычный Enter продолжает текущую обычную отправку; Shift+Enter оставляет новую строку.
- Над input показывается общий компактный список queued items. Каждый item имеет Send, Delete, pencil Edit. Send отправляет **ровно выбранный item**, только по явному нажатию пользователя.
- Порядок списка — порядок добавления, oldest first. Пользователь вправе выбрать любую строку для отправки: FIFO здесь означает порядок списка, а не запрет ручного выбора. Нет обещания общего FIFO между queued items, обычным Enter и входящими agent/system messages.
- Любые смены состояния агента, окончание turn, новые сообщения, restart/reload, открытие чата и возвращение online **никогда не вызывают Send**. После успеха не отправляется следующий item.
- Edit меняет сохранённый unsent item в его текущей позиции. Это не restore-as-draft и не добавление нового item. Save/Cancel независимы от текущего composer draft.
- Переключение чата, recipient, root или context не переназначает существующие items. Очередь сохраняется после restart приложения.

Bounded payload scope: ordinary text, direct `do` **или `ask`** mode; group сохраняет существующий `do`. Mode записывается в queue item, отображается при необходимости и сохраняется при inline edit. Без attachments/file chips, cross-team, slash commands, revision/review submission и delegate mode. Это ограничение payload, **не исключение chat type**. Для несовместимого содержимого queue action disabled с видимой локализованной причиной; Cmd/Ctrl+Enter не отправляет такой payload, не очищает draft и не silently strips ничего. Обычный Enter сохраняет прежние rich workflows. Текстовые mentions/task references допустимы: существующий preparation/resolution helper остаётся авторитетным источником outbound text/taskRefs. Direct ask использует тот же buildPreparedSendRequest/actionMode transport, не новый workflow.

## 3. Самая маленькая архитектура

Feature `src/features/manual-message-queue/`:

- `core/`: plain serializable identity/record types, очередь и допустимые переходы состояния, revision validation. Без React, IDB, Electron, providers или renderer-type imports.
- `renderer/`: один queue hook, одна QueueList с inline editor, concrete persistence adapter, narrow direct/group transport adapters. Public renderer entrypoint; никакого main/preload/MCP/API слоя для queue.
- Wiring в existing composer boundary; current send callbacks/API остаются transport. Shared outcome classification/context latch вынести в маленький существующий renderer helper только там, где это реально устраняет расхождение правил. Не строить новый submission framework.

Record v1 содержит: **queueItemId**, revision, monotonic position, createdAt/updatedAt, stable scope, captured route, editable text, actionMode (`do`/`ask` direct, `do` group), state; при каждом dispatch — отдельный новый **attemptId/messageId UUID**, frozen outbound request. QueueItemId и transport UUID — разные identities. State sending + frozen request сами являются durable dispatch-intent marker; отдельный transportStarted flag/transaction не нужен. Scope = stable transport/context identity + effective configured **team transport** root binding + teamName + chat identity. Direct chat identity содержит normalized participant; group scope содержит groupChatId, recipient сохраняется **в каждом item**, а не в key всего group списка.

Root binding привязан к **реальному existing team transport**, а не к root выбранного session browser. `GroupChatStorage.safeGroupTeamPath` читает `getTeamsBasePath()`; `pathDecoder.getTeamsBasePath()` = `getClaudeBasePath()/teams`, то есть local effective configured Claude root. Main teams IPC использует один `getTeamDataService()` и native controller создаётся с `claudeDir: getClaudeBasePath()`. Поэтому для direct/group queue persist tuple: transport=`desktop-local-teams-v1` + `api.config.getClaudeRootInfo().resolvedPath` + activeContextId + stable context/connected-host identity + team/chat. При SSH выбранном context `api.ssh.getState()` нужен только для authoritative host identity и agreement с active context (`ssh-${host}`)/connectedHost; `remoteProjectsPath` является **session projects** path и никогда не применяется как team storage root. Никаких remote writes/нового SSH team backend не добавлять; queue вызывает ту же team API, что ordinary send. Source: `src/features/team-group-chats/main/infrastructure/GroupChatStorage.ts:20`, `src/main/utils/pathDecoder.ts:405,426`, `src/main/services/team/TeamDataService.ts:461`, `src/main/ipc/teams.ts:859`, `src/shared/types/ssh.ts:56,77`. Пока resolved team root/config не загружен или SSH identity disagreement, queue actions blocked с причиной. Для каждого manual Send дополнительно capture и перепроверить existing request epoch и binding перед transport. Process epoch/connectionState не входят в stable persisted key; новый API не нужен.

Persist использовать тот же существующий IndexedDB object store через `composerDraftReadwrite`, с отдельным новым prefix/schema (`manual-message-queue:v1`), без миграции working/recovery records и без изменения старой схемы. Queue index хранит authoritative порядок; не сортировать по updatedAt. Decode malformed/unsupported record — явная ошибка и запись не перезаписывается. Для очереди требуется durable commit: при IDB failure сохраняется current draft и ошибка, без silent memory-only enqueue.

Один store transaction для enqueue: проверить persisted working revision/snapshot → записать queue item/index → clear только **тот же** captured working revision → commit. До этого дождаться flush и **отклонить enqueue при memory-only working persistence**, сохранив composer и объяснив отсутствие durable сохранения; не копировать stale IDB draft вместо актуального in-memory текста. UI clear применить через существующий `draft.adoptWorking` с loadGeneration/localEditCounter guard; новый ввод пользователя после нажатия не теряется. Direct hook уже предоставляет flush/snapshot/adoptWorking; использовать их. Для group hook нужен narrow queue-consume adapter: дождаться его session persistence chain, проверить durable working результат, передать working revision/text/recipient, обновить revision после commit и очистить React text только при совпадении current address/text/recipient. Не использовать group.send для enqueue.

Edit/Delete выполняются compare-and-set по item revision/state в том же store. Item ordinal/queueItemId при edit не меняется. Каждая новая допустимая отправка создаёт новый attemptId/messageId, включая отправку после доказанного before-call cancellation или authoritative pre-canonical rejection: старый frozen attempt очищен, а edited payload никогда не использует ранее attempted message UUID. Unknown не redispatches. Persist scope/root/chat остаётся неизменным. Это предотвращает потерю данных при remount/другом экземпляре UI; не добавлять distributed locks/leases.

## 4. Отправка без перезаписи draft и без расширения group framework

**Предпочтительный минимальный вариант:** queue record остаётся владельцем своей попытки. Atomic claim `queued → sending` сохраняет frozen request/UUID до первого transport call. Working draft не участвует в manual Send. Нет временного load queued item в composer, clearDraft или beginAttempt с фиктивным `workingCleared:true`.

Это снимает необходимость расширять `ComposerPreparedRequest` и draft repository group request вариантом только ради очереди. Existing direct/group обычные sends и group frozen retry остаются прежними. Для direct transport переиспользовать current onSend и существующую transport outcome классификацию; для group — `api.teamGroupChats.send` с captured group/recipient. Новый group queue request contract — маленькая serializable route + frozen GroupChatSendRequest, без нового backend/receipt protocol.

Existing recovery/outbox **правила и presentation** переиспользуются для sending/unknown warning, duplicate-risk wording, copy и messageId reconciliation. Queue records не выдавать за существующие draft recoveries и не дублировать одновременно в двух durable хранилищах. Unknown queue attempt отображается в том же queue container frozen строкой с delivery status. Это отдельный пользовательский unsent/attempt record; existing pending inbox и recovery outbox остаются отдельными. Если общий status UI сейчас слишком связан с recovery actions, извлечь маленький reusable presentation helper, а не весь outbox controller.

Переиспользовать current context-wide submission latch, чтобы ordinary Enter и queue Send не стартовали одновременно в одном context: narrow try-acquire/release helper вокруг существующей map, освобождение в finally. Он вызывается в **трёх** местах: existing direct runComposerSubmission, existing ordinary `useGroupChatComposer.send` (сейчас latch там отсутствует) и queued Send. Group acquire идёт до first await и до попытки frozen UUID/working persistence; failed acquire оставляет current draft/attempt без изменений. Persisted item CAS дополнительно защищает double-click/другой UI экземпляр. После successful claim повторный click не может вызвать transport. Есть **одна ручная отправка за действие**, без head-drain, timers/subscription triggers и runtime readiness.

Порядок manual Send:

1. Проверить item queued, свежую revision, root/context/chat и текущую структурную send eligibility. Не проверять idle/busy; user Send имеет обычную transport семантику.
2. Acquire existing context submission latch. Подготовить текст/request существующим preparation helper; transport target берётся из item, не из текущего selector.
3. Один atomic claim генерирует **свежий attemptId/messageId**, отличный от queueItemId, сохраняет immutable request/attempt UUID и state sending; commit обязателен до transport. Это dispatch-intent marker, **не** доказательство выполнения call; второго transportStarted write не делать. Если live owner этой попытки точно знает, что call не начался (guard изменился), разрешён CAS возврат sending→queued с очисткой frozen attempt только для той же claim revision. Любой crash после durable claim консервативно unknown; ложная повторная отправка дороже false unknown.
4. Вызвать **один** existing direct или group transport. Не изменять working draft.
5. Positive admission/canonical save → удалить item из queue durable state, обновить существующую историю. Следующий item остаётся queued. Ошибка refresh не вызывает повтор send.
6. Unknown outcome → сохранить frozen unknown item. Recovery hydration переводит persisted sending в unknown **только если active-attempt registry не владеет этим attempt UUID**. Live React remount/unmount/rerender не превращает действующую отправку в unknown: shared narrow owns-active check использует тот же context latch/attempt id; инициированная Promise завершает durable settle независимо от mounted component. После process reload registry пуст и оставшийся sending консервативно unknown. Отправка при recovery никогда не вызывается. Edit/Send запрещены после dispatch claim, кроме **двух** доказанных возвратов в queued: live before-call cancellation и authoritative known pre-canonical rejection. В обоих случаях CAS очищает old frozen attempt, queueItemId/позиция сохраняются, следующая отправка получает fresh transport UUID.

Unknown Send и Edit disabled. Явная action «Проверить в истории» сравнивает loaded canonical user message **exact messageId + captured scope/root**, refresh только по user action; подтверждение удаляет queue record. Отсутствие echo не возвращает record в queued и не доказывает failure. Copy доступен. Delete неизвестной попытки — однозначно **«Убрать запись»**, только забывает локальный record. Для unknown постоянно показывается видимое предупреждение: «Доставка неизвестна. Удаление записи не отменит сообщение; повторная отправка текста может создать дубликат». Tooltip и aria-label trash action прямо говорят «Убрать запись; доставка не отменяется». Modal не нужен; silent ordinary Delete label недопустим. Нового resend действия нет.

Group result `saved:true` — canonical post сохранён, даже если часть fanout queued/failed/unknown или statusPersisted false. Удалить unsent queue item; показывать canonical history message и существующую status/error presentation, **не** повторять весь fanout. Не добавлять новый delivery-summary framework. Authoritative known pre-canonical group validation rejection из existing deterministic error-code списка возвращает editable queued item с причиной и очищает rejected frozen attempt; следующая user Send использует fresh attemptId/messageId. Transport exceptions direct всегда unknown, потому что stdin мог сработать до failure. Остальные exceptions group тоже unknown; **для unknown** никакого автоматического или fresh-UUID resend.

Существующий обычный group composer unknown retry сохраняет frozen text/recipient/UUID и remains immutable. Он не переносится в UI queue и не редактируется через QueueList. Новый queued item имеет право быть editable только до собственного transport start. Не переиспользовать ранее attempted UUID для изменённого payload.

## 5. Group, archive и смена membership

- Standard Group All использует DEFAULT_TEAM_GROUP_CHAT_ID + group send, как сейчас. Existing стандартный selector, который переводит в private member composer, продолжает быть direct transport — это другой chat route. Custom group member selector никогда не становится private transport.
- All означает всех актуальных членов группы **при manual Send**, как существующий API. Не freeze arbitrary recipient subset на enqueue и не добавлять новый API recipients[]. После canonical save authoritative frozen recipients/run keys остаются ответственностью existing group service.
- Directed group item сохраняет recipientName на enqueue; смена current selector не меняет queued recipient. Перед Send проверить actual current group membership/available recipients; removed или unavailable recipient блокирует именно этот item с причиной. Не переадресовывать в All/lead/другого member.
- Archive/deleted group/team, недостаточно участников, no compatible run: Send blocked; queued text не исчезает. Edit/Delete unsent records остаются user-only и допустимы. Group authoritative main validation остаётся последней проверкой races.
- Direct member removed — Send blocked; когда существующие agentId/joinedAt доступны, capture/revalidate их для обнаружения remove/re-add с тем же именем. Runtime restart сам по себе не блокирует ручную отправку на тот же member/chat. Если стабильная entity identity отсутствует, договор адресации ограничен name в existing app; не обещать detection полного пересоздания одинакового team/member namespace.
- Root/context change during save/claim/call: до transport — no call, сохранить текст; после transport start — frozen unknown/observed result в исходном scope, никаких результатов/clear в новом chat.

## 8. Оценка bounded реализации

All-chat manual text queue с inline edit, durable root/chat/recipient scope и sending/unknown boundary: **650–950 production LOC + 300–480 essential test LOC = 950–1 430 LOC**.
