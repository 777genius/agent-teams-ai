## Established failure and its limit

The original d4b Main job 140953507815, run 46131875301, performed one trusted first Send and then timed out waiting for its original source receipt. The exact retained profile has Alpha/Beta lead delivery bindings but no `runtime` or `management` field and no retained Runtime/launch originals. Their command directories contain the initial task seed receipts only. The screenshot shows the optimistic bubble as Delivery unknown. Neither the private attempt record nor the exact IPC refusal was retained, so the diagnosis must not assert which earlier guard returned first.

There is, independently, a deterministic source admission blocker. Actual TeamHost always supplies an inputPreflight closure and throws hold if no RuntimeTeamCoordinator exists. Merely putting a delivery tuple in a Team definition does not supply captured input policy. The Cross-Team composition calls that closure with the complete formatted target input before the source receipt/outbox/target publication. Its generic `runtimeInputFits` fallback is reachable only when a separately constructed composition omits the callback; it is not the actual TeamHost branch. Ordinary `team.execute/message.send` to a delivery-bound member has the same required policy boundary. Root's reviewed P1 policy is preserved.

A legitimate positive exists. A strict original Host runtime profile creates MemberEntry metadata during construction; `createMemberEntry` does not allocate a provider. Fresh preflight uses that exact entry's current binding, original Team authority and inputBytes. Runtime admission can retain an unopened input. `kick()` dispatches only an attached allocated nativeReady Runtime; it never opens one. Thus configured-but-unopened input admission is different from unconfigured delivery and does not require a native launch.

The legacy Main CrossTeamService's offline inbox behavior and `requireRuntimeDelivery` option do not establish authority for the strict Host request. No new Host product-only capability is invented here. The renderer's swallowed refusal/unconfirmed presentation is a separate, still-open error-parity review; this fixture correction does not silently convert a refusal to sent or retry a command.

- The exact three-definition combined fixture: unbound base board Team plus Alpha/Beta above, exactly those two runtime members, exhaustive equality against the builder's profile fields, exact scopes/delivery/principal grants, no extra runtime fields or members and no management. The adapter may use its normal read locks/directories; it creates no Runtime row or native authority. Retain those bounded observations in the existing proof object.
