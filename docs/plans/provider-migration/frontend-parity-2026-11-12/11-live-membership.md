## 3. Chosen connected design: one derived admin action on the same original request

Keep the public full-roster payload and public receipt unchanged. Keep normal offline replace and its released-Runtime guard unchanged. Host privately routes to the new finite live branch only after it has the original captured Team, current actor, expected roster revision, actual retained run/lead and full request. The branch classification reads the original target's retained launch/binding/control/custody evidence before taking an offline shortcut. In particular, remove with retained target debt uses the exact cleanup branch even when the mutable active Team/run is absent. Add/restore on a genuinely stopped Team remains saved-only; it cannot use that rule to conceal unresolved original target debt. The old alive OpenCode-led refusal is still tested against actual alive topology, not inferred from an arbitrary historical OpenCode launch.

Under the original Team fence, derive exactly one of:

- **add:** one genuinely new non-lead product member, no other member or Team setting change;
- **remove:** one existing non-lead member disappears, no other member or Team setting change;
- **restore:** one exact previously removed member returns with its original product ID and requested original saved settings, no other member or Team setting change.

Use the existing members()/schema/normalization rules and command-derived add ID. Case-only renames, ambiguous remove+add, lead replacement, changed peers, changed Team settings and multi-target edits do not enter this branch. They retain the original offline replacement behavior/refusal. A Renderer claim of “add”, a display provider label or a supplied source binding is not authority. Actual live OpenCode-led topology retains its old refusal.

The first admission freezes original principal/authority revision, command/full request fingerprint, expected roster revision, actual launch/capture, exact target before/after rows, unchanged peers/settings commitment and original action budget. The same command cannot cross an operation or Team. Duplicate original ID or lookup reads the original intent/result, never derives another operation from today's roster. Exactly one unresolved live membership decision per Team is permitted under the existing fence; a replacement ID cannot hide it. The private two-phase add/restore continuation below is part of that first admitted execution, not a duplicate public invocation or a retry route.

No new owner, command journal, sidecar state file, public RPC, general transaction framework, scheduler or retry loop is introduced. The finite helpers only use:

1. the existing **StoredRosterReceipt in state.json** for this original admin decision and final product result;
2. the existing **TeamLaunchRecord** for actual target expected selection, attempts, original closure and fresh generation/capture references;
3. existing management receipts, Runtime/session records, endpoint owner and worktree receipts for their own resources.

A pending private roster receipt does not make public lookup successful. Its private phase and fingerprint are validated before the old success projection. Original records without the optional extension retain their exact old meaning and validation. Retain existing 1024 roster commands/removed rows, 256 active members, 1 MiB state/launch limits and command-size limits. New live selection rows share a finite 64-transition allowance with the existing member-action/restore history when the extension is present; this is not an extra independent 64-row ledger or a retroactive rejection of an unchanged legacy record. Reject capacity before new allocation.

## 5. Publication, exact live effects and failure handling

### Add / restore

Retain a prepared admin receipt before awaited work. Once full current preparation/capture is ready, publish the one target membership/selection under the same original revision/authority; preserve every peer delivery/grant and all canonical Task/inbox bytes. The launch helper appends/selects only that target's expected entry and original attempt; target creation is recorded before native claim.

Install the actual target entry in the existing registry and the same array used by the original launch callbacks. The current array contains exactly the selected entry per member. Prior target entries remain retained by full binding for cleanup and history; an old .find(memberId) must never capture the restored target's new commands. Call the original startMember once and retain its actual allocation, readiness/context and failure outcome under the original timeout. Do not report a completed product operation merely because its row exists, a promise was created or a helper process was allocated.

If preparation refuses before target publication/allocation, settle that original failure without changing membership only after the original preparation/probe resources are proven released. Unknown probe cleanup remains held even when the roster is byte-identical and no target Runtime ever existed; no terminal compensated rejection may erase that debt. If failure occurs after target publication/allocation, use the same original target close/provider/endpoint cleanup before any successful compensation. An exact inverse target metadata change is allowed only against the receipt's own published successor and unchanged peer commitment. Never restore a whole previous state snapshot over newer Task, grant or other-command writes. Worktree effect evidence remains in its original owner; cleanup does not remove unverified paths.

A completed compensation records the original operation as rejected, not not-dispatched. Unknown target closure, source/currentness loss or an unconfirmed metadata write remains held with its original debt. No auto retry, peer restart, fallback provider, recapture, inferred absence or false rollback-success receipt. Historical rows remain available for the same original owner to reconcile/release.

### Remove

First select the exact original member and every retained original binding/debt of that target relevant to this live run. Seal and stop only that target through the existing close path. A late mutable “Team is stopped” or missing active map entry cannot bypass its retained custody. Do not stop the Team or visit peers as a substitute.

Publish product removal and revoke only that target's active grant after original Runtime closure/provider cleanup/endpoint cleanup are proven. Retain removed product settings/history. The launch record keeps a validated retired selection/tombstone for that exact target; it is not a fake Skip or a vanished launch row. No new native model inference is needed.

This order avoids the common old persist-before-detach rollback window. If original closure or publication is uncertain, retain the same original decision and its evidence. Recovery may finish only an already decided metadata projection after validating its exact preimage; it cannot relaunch the removed target, replay Stop or call a different owner's process. Best-effort compensation is never represented as restored native readiness. This is the explicit truthful failure boundary, rather than a promise of atomic rollback that old code did not provide.

### Original ledger result

The backend already has outcome rejected. Main must keep a closed result union in its existing roster ledger: original successful receipt or exact confirmed terminal rejection. The generic ledger's applied reconciliation state means “this original command's result is settled”; it does not become a product-mutation assertion when the domain result is rejection. Do **not** use its not_applied route: ApplicationCommandRunner can retry that route. Unknown/missing Host evidence stays unknown. Cached completion still performs original Host/current-owner lookup before disclosure. Return the existing public failure shape, without a new state/status field.
