# Bounded feasibility after the W05/W07 map

Source/read-only only, at `ac03d91bcd4d5678c653e09624978fffdc8f2784`. No scenario, source afterimage or additional workflow is selected here.

## W05: engineering composition is possible with existing ownership interfaces

The available finite Windows pieces already use the actual Main `captureMainWindowsCustody`, `CapturedHostClient`, original Windows Jobs, original query HANDLE witnesses and the real Host/D adapters. `nativeEmulatedProviderGate.ts` wraps the existing `HostCustodyOwner.attach(...).handle(...)` for observations. The source A/B helper uses the same seam, captures the original suspended root witness before returning `prepare`, and retains original cleanup; it does not need a new provider API to observe a fault or to reconnect the existing public Host client.

Separately, `nativeFacadeScenario.ts` has the actual `installOwner` hold and a pre-resume cancellation branch. Existing `capturedHostClient.test.ts` has a deterministic lost-write-ACK/replacement-Host composition and a committed-effect UNKNOWN/no-replay case. These establish reusable interfaces, not the missing full result.

**There is no demonstrated drop-in mode that already does the missing installation crash.** A hold before forwarding `prepare` is a pre-installation fault; a hold on a later Main `resume` RPC must not be mislabeled as the Host's owner-install callback. A prospective TEST-only composition must identify the actual callback boundary and join an original Host exit to the original durable command, UNKNOWN/cold lookup, no replay and original Job cleanup. It may reuse the existing finite peer and TEST barrier patterns without adding provider/public authority semantics. It still needs its own bounded source proposal and original native result. Current source alone does not establish that the complete sequence fits an existing scenario clock.

After-tool-effect loss can likewise reuse the real command/journal and existing finite lost-ACK pattern. Merely crashing after a successful terminal reply would leave the original W05 UNKNOWN condition untested. No new signal/PID adoption, automatic retry or replay is justified.

## W07: existing public operations suffice, but the fresh-launch suffix is new acceptance work

The finite Windows Claude source A/B branch already calls the original `runtime.checkpoint`, `runtime.restore`, `runtime.read`, ordinary new-input delivery and `runtime.stop`. It distinguishes the same native session from the new generation and keeps repeat restore allocation-free. A separate, explicitly selected fresh launch after that second Stop could use the original launch/open path and original profile/source admission, then require a distinct native session/generation, no restoration/replay, and original cleanup. That is an engineering-test extension; it is not a missing new Runtime API or permission to append an unchecked action to Plan61.

The OpenCode V2 embedded Host helper also already owns checkpoint/restore/Stop and native model/history assertions on Windows. It can be a reusable native test pattern, but its V2 transport is not the P08 Windows V1 baseline. The supported Darwin Desktop Resume helper cannot supply the Windows tuple. No reviewed existing Windows V1 full Resume-plus-fresh mode can simply be switched on, so this review does not claim such a route exists or invent a Darwin substitute. A separate original-plan selection would have to bind the supported Windows V1 recipe/history contract and actual original cleanup within unchanged budgets.

## Qualification boundary

Finite Windows additions can close engineering gaps without any genuine Claude/Codex invocation. They cannot, by themselves, satisfy P08 §6's actual CLI/SDK requirement for those vendors. Genuine Claude/Codex qualification remains prohibited; an existing localhost model endpoint does not change that. Allowed genuine OpenCode native work remains possible after a precise Windows/provider selection, but neither a V2 PASS nor an unsupported V1 assumption may be substituted for the specified baseline.

The practical order is unchanged: finish selected Plan61's original routing only, preserve the original same-Main/C8/B2 gates, then separately select any required W05/W07 acceptance extension. No whole-goal block or new product feature is asserted.
