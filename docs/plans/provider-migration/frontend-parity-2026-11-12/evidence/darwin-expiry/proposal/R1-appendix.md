### 2. Existing order and the test boundary being amended

The original generated Host fixture starts its short deadline with `performance.now()+20` before calling `HostCustodyClient.request`. That method validates the call before `requestWhenReady` computes and checks its fixed deadline. `resumeAdmission` checks expiry before invoking the lazy builder/schema parse; `dispatch` checks the same deadline again after that builder. Any legitimate early refusal can fulfill the ordinary Host handler without sending a private native frame. These checks are production behavior and stay byte-exact.

On a dispatched request, the unchanged Host output shares its bounded queues and emits the existing private envelope. Main decodes and validates the envelope and binding, derives the original entry deadline from the received remaining budget, creates the actual `NativeRequest`, calls `nativePending.set`, then installs that entry's timer and calls `pumpNative`. The existing TEST completion gate already intercepts that real Map insertion and the original child-stdin completion callback. It holds the callback after the actual child write has completed, preserving Main's large original write-byte reservation. `gate.queued` observes real Main admission; it is not a fabricated or guessed admission signal.

This proposal changes where this fixture applies its short interval: from a pre-schema Host caller deadline to the actual Main entry after insertion and before Main installs its existing timer or pumps. It retains a 20ms short interval, but **does not preserve the old end-to-end 20ms scope**. The generated Host request now uses its existing default 2000ms fixture transport timeout for setup and transport; the expiring case no longer overrides that default with a Host-side 20ms deadline. The outer request remains3000ms, the existing Main write timeout remains500ms, and production deadlines, admission checks, runtime/provider budgets and controller limits are unchanged.

The inserted entry receives `Math.min(value.deadline, performance.now() + 20)`. This can only shorten its already-established Main deadline. It never increases that deadline, creates another timer, starts another request or replaces the entry. The deterministic property is the order of insertion, cap and original timer/pump; it is not immunity to arbitrary stalls beyond the existing setup/write/request bounds. Replacing `request` with `requestWhenReady` alone would still leave real validation, scheduling and dispatch before Main and would not establish this ordering.
