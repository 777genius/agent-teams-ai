No new HTTP/business marker, automatic input, retry, replay, native owner, production RPC or currentness exception is needed for this design.

No new workflow, matrix member, runner, deadline or reset of an earlier case is proposed. Whether the whole existing job fits its budget is an actual execution question, not a claimed result.

## 5. A concrete original-driver deadline issue to resolve before reuse

The existing P11 driver's local `poll` at89–94 captures `Date.now()+90000`, awaits a read, and then accepts a true result without a post-read deadline check. A read that resolves true after the cutoff can therefore be accepted. This is a source-backed control-flow observation; no actual CI cause, elapsed timing or historical failure is inferred.

A future bounded proposal cannot claim strict original deadlines while copying that behavior. Preserve the original 90-second budget and100ms cadence, but require the same cutoff after the awaited read and before success, with a meaningful late-success negative through the actual helper seam. That is a stricter same-budget check, not permission to increase a timeout, retry the original mutation or add another UI action. If the root does not authorize that narrow prerequisite, the old driver should not yet be called a review-ready target for reuse.
