**Original Job custody after a dispatched Stop.** Microsoft's primary [AssignProcessToJobObject documentation](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject) describes inherited child membership in the existing Job chain and failure to assign when a Job in that chain is terminating. [TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject) describes termination of associated processes and nested child Jobs. These are API premises for the candidate mechanism, not proof that any historical P08 or process failure had this cause. In `Scopes.capture`, the source retains the same original CREATE-event process HANDLE, PID/birth/object equality and outer membership. It pins a shared original record whose successful termination-dispatch latch and fresh `IsProcessInJob` observation match that same child, before the existing retirement scan. If assignment of the child's own new Job fails, it retains the original assignment error, requires that proof again, duplicates only the already retained original terminating Job, closes the empty newly created Job, and marks the child record `inheritedTermination`. Missing/failed proof preserves the original assignment failure. The temporary pin is confined to the current admission; the debug record then owns one bounded duplicate of the original Job until the unchanged original absence/retirement rules permit release. This does change which existing Job that debug record retains; it does not create a historical cache, reopen a PID, acquire a different process, or mint parent service authority.

**Public authority and lock/deadline boundaries.** `findService` rejects inherited records; current registration, exact registration, Query, Stop and settlement cannot use such a record as a parent's service scope. The debugger may use it only for its original child's startup-event state and eventual retirement. Existing key monotonicity, current-event PID collision checks, record cap, original process/Job observations, unknown/error handling, outer containment and cleanup remain. Stop latches `terminationDispatched` only after a successful original `TerminateJobObject`, under the existing registry mutex. It adds the deadline recheck after acquiring that mutex; registry delay therefore spends the same original admitted budget. Waiting for original process exit and zero Job accounting remains outside the mutex. No Stop replay, widened budget, early absence or new public wire opcode is authorized. The fallback can use any already proven terminating Job in the child's original nested chain because the debug-only record confers no service operation; it does not select a new process through ancestry or a census.

**Finite startup-event handling.** `StartupBreakpoints` replaces the former one-breakpoint boolean with per-original-HANDLE state. A dynamically loaded `IsWow64Process2` query uses rights already retained by `retainProcess`; its primary [API documentation](https://learn.microsoft.com/en-us/windows/win32/api/wow64apiset/nf-wow64apiset-iswow64process2) allows the existing limited-query right and identifies the emulated process architecture. Absence of that API grants no extra x86 exception; query errors refuse. Only explicitly identified I386 processes may accept one first-chance `0x4000001f` after the first native breakpoint. Later, out-of-order and second-chance exceptions remain unhandled by this startup state and go through the original debug continuation path. The source introduces no static import of that optional API. This review does not assert that a complete two-event sequence has already been observed on either current runner, or that every supported Windows tuple was newly qualified.
