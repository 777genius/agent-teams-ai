## User behavior and invariants

One optional 👍 action and one count/name tooltip on a **persisted canonical group message**. This includes standard Group chat **All**, custom-group posts/replies, and that same custom post displayed in the standard team feed. All projections share one persisted set. Standard default-lead legacy traffic, DM/cross-team/transcript-derived rows and unsent queued rows have no reaction action in this MVP; no ID migration or explanation banner is needed on each unsupported row.

Human click adds/removes only the human's own 👍. Agents get one idempotent **add acknowledgement** tool; no emoji argument/picker, no agent edit/remove tool. Count equals unique actors; tooltip names come from the same complete set. Preserve the configured actor name in storage; roster removal does not erase historical counts/names. Existing reactions remain visible after archive; archived groups reject changes. Reactions acknowledge a message, not task completion or automatic proof that everybody read it.

A reaction writes **only its reaction store** and emits a renderer/HTTP refresh event. It never writes an inbox message, calls delivery, wakes another runtime, changes tasks, increments ordinary unread/attention, or creates an acknowledgement reply. A human may react while runtimes are stopped. An agent must have a current compatible reaction consumer and a physical inbound for its own member/run; no admission probe of other members is needed.

## Narrow contracts and single persistence owner

Extend the existing `team-group-chats` feature rather than adding a messaging/reaction framework.

| Consumer | Operation | Result / invariant |
| --- | --- | --- |
| Renderer | `getReaction({teamName, groupChatId, messageId})` | `messageId` must be an existing canonical UUID in that group; returns `{groupChatId, messageId, actorNames, canReact}`. `canReact` depends on archive/target validity, not model availability. |
| Renderer | `setReaction({...target, active:boolean})` | Actor is implicit `user`, supplied by the IPC/trusted human adapter, never by renderer payload. Returns committed snapshot; repeated same state is a no-op. |
| Agent tool | `group_chat_react({teamName, from, groupChatId, relayOfMessageId})` | `relayOfMessageId` is its physical inbound ID. Main resolves the canonical UUID from the persisted member inbox and adds only that actor's 👍. Structured success echoes exact group, canonical ID, physical inbound ID, actor and the committed `groupRunKey`, including a newly replaced proof on an existing actor. No new logical message UUID. |
| OpenCode completion | Internal `hasAcknowledgedInbound({teamName, groupChatId, memberName, inboxMessageId, runId})` | Bounded atomic snapshot read requires one unique exact group/physical/actor/run proof. Its reaction entry supplies the canonical UUID already validated at mutation; malformed/ambiguous proof is false/error-safe. No registry/inbox lock, runtime/MCP probe, new ledger field, renderer/MCP mutation API or fabricated visible-message proof. |

Implement reaction coordination in one small `main/application/groupReactions.ts` module composed by `createTeamGroupChatsFeature`. Reuse `GroupChatStorage` path checks, bounded reads, file lock and atomic-write helpers. Add `withReactions` to that owner; do not create another generic repository or duplicate these filesystem policies.

Persist `group-chat-reactions.json` per team, version 1. Each entry is `(groupChatId, canonicalMessageId)` with actor records: configured name, `reactedAt`, and **agent-only** physical inbound ID + actual `groupRunKey`. Human records have no runtime proof. Emoji is implicit 👍; count is derived, never stored independently. Missing file is empty. Corrupt/oversized/unsupported storage returns a storage error and is never overwritten as empty.

Mutation validation: bounded inputs and safe team path; group exists; canonical `inboxes/user.json` target has `messageId === groupMessageId`, protocol 1 and matching group. Agent addition additionally requires current membership, a stored physical row with `to === from` and exact group/canonical identity, and its `groupRunKey` matching the actor's current admitted run. Use the existing app-bound controller authorization boundary and reject reserved `user` on the agent endpoint; do not claim it introduces new per-member cryptographic authentication. Read runtime proof outside inbox locks; only the actor is probed. Serialize archive/membership decision through the existing configuration/registry boundary, then reaction-file mutation; preserve the existing registry → inbox/reaction lock direction. No delivery call occurs.

Duplicate add for the **same validated physical inbound and run** returns the existing record unchanged. A valid fresh same-actor acknowledgement for a different physical inbound or current run replaces only that actor's consumption proof, retains its original name/`reactedAt`, and still counts once. Its structured success returns exactly the newly committed proof; a stale/unsupported request cannot replace proof. Human removal removes only `user`; concurrent additions by different actors survive the locked read/modify/write. Publish `group-reactions` refresh only for a visible actor-set change. Proof-only replacement is persisted and returned without a renderer event because count/names did not change; it never emits an inbox event. Failed writes and unchanged retries emit nothing. Archive can return an unchanged existing snapshot for an exact same-state/proof retry, but cannot admit a new actor or replace proof.
