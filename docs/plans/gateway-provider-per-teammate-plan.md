# План: Gateway-провайдер с выбором и учётом на каждого тиммейта

**Статус:** v9 — замечания ревью PR 942 закрыты: approval snapshot в usage source и durable неполнота при правке секрета; реализация начинается с §8
**Тестовый стенд:** локальный [agent-teams-ai/sub2api](https://github.com/agent-teams-ai/sub2api)

## 1. Цель

Каждый тиммейт (Claude Code, Codex, OpenCode) **отдельно** выбирает:

- провайдера и модель (per-member поля `providerId`/`model` уже есть),
- gateway-подключение: профиль (endpoint) + **свой** API-ключ (новое),
- его расходы учитываются **отдельно** от других тиммейтов.

Наш будущий backend и sub2api (стенд) обязаны уметь одно и то же — контракт §3.

## 2. Границы скоупа

**Входит:**

1. Per-member gateway-биндинг: профиль + персональный API-ключ тиммейта.
2. Доставка биндинга в спавн трёх рантаймов (§5), включая per-member env и Codex overrides в
   bootstrap-пути (работа в репо оркестратора — §5.1, шаг 3а).
3. Учёт расходов per-member (`gateway_exact`) в token-usage, `byAgent`.
4. UI: выбор профиля/модели на строке тиммейта, управление профилями.
5. Прогон сценариев §8 на локальном sub2api.

**Не входит (явно):**

- управление пулом аккаунтов/группами/ротацией — это админка бэкенда;
- биллинг, квоты, новые per-member бюджеты; совместимость существующих
  global/team/project бюджетов при изменении атрибуции сохраняется (§6.3);
- **лид команды** — вне gateway-биндинга, использует своего провайдера;
- OAuth/subscription через gateway — только API-key режим; рантайм вне
  API-key режима → блок биндинга с ошибкой (единое правило);
- миграция `anthropic.compatibleEndpoint` и `codex.customProvider`;
- HTTP-адаптер фичи — desktop-only (осознанное исключение из standard);
- деплой sub2api в приложение;
- импорт учёта с субдневной точностью (§6 — агрегаты по дням);
- распределение дневных gateway-расходов по сессиям, задачам и проектам;
- перенос существующего ключа между endpoint-ами/автоматическое распознавание
  URL-алиасов одного gateway: новый endpoint требует нового ключа (§4);
- сверка gateway с CLI-логами и резервный локальный учёт gateway-запусков:
  у такого запуска один источник расходов — gateway (§6);
- стабильные id тиммейтов/команд — идентичность биндинга по имени, как и
  везде в token-usage (run-identity `team:…:member:…`); смена имени =
  ручная перевязка с новым ключом; старый ключ сохраняет исторического
  владельца (§4, §9).

## 3. Gateway-контракт

| Потребность                   | Эндпоинт                    | Auth          |
| ----------------------------- | --------------------------- | ------------- |
| Anthropic Messages            | `POST /v1/messages`         | ключ тиммейта |
| OpenAI Responses              | `POST /v1/responses`        | ключ тиммейта |
| OpenAI Chat Completions       | `POST /v1/chat/completions` | ключ тиммейта |
| Каталог моделей + проба ключа | `GET /v1/models`            | ключ тиммейта |
| Учёт по ключу                 | `GET /v1/usage`             | ключ тиммейта |

Пути фиксированы контрактом — настраиваемых путей в профиле нет.
`baseUrl` — корень gateway без завершающего `/v1`; при сохранении URL
нормализуется (завершающий `/` и однократное снятие `/v1`),
разрешён HTTPS; HTTP — только для loopback (`localhost`, IPv4 127/8, IPv6 `::1`)
локального стенда. Userinfo/query/hash запрещены; удалённый HTTP отклоняется
при сохранении и prepare, ключ по нему не отправляется. HTTP-клиент добавляет
`/v1/...`, маппинги Codex/OpenCode — нужный их клиентам `/v1` ровно один раз.
Для частного **не-loopback** адреса требуется `allowPrivateNetwork` профиля
(по умолчанию false). UI использует обычный shared Checkbox по существующему
образцу `LocalProviderPrivateNetworkApprovalControl`; второго диалога/пробы нет.
Классификация совпадает с `normalizeRuntimeLocalProviderTarget`: существующий
чистый hostname-helper выносится в shared для двух потребителей, без deep-import.
Это проверка hostname из URL (IP-литералы и `.local`), как у текущих local
providers. Обычное HTTPS DNS-имя может разрешиться в частный IP; HTTP-клиент
и native CLI разрешают DNS штатно. DNS pinning и защита от rebinding требуют
отдельного сетевого scope и в этот этап не входят.
Сохранение/проба/prepare проверяют разрешение одинаково для всех рантаймов;
при смене canonical URL подтверждение сбрасывается. Loopback и публичный HTTPS
не требуют подтверждения; удалённый HTTP остаётся запрещён независимо от флага.
Единица учёта = API-ключ (один ключ на тиммейта ⇒ сервер различает тиммейтов
без своих заголовков; уникальность ключа обеспечиваем на своей стороне, §6).
Учёт через gateway `/v1/usage`, а не панельный `/api/v1/usage`: панель требует
JWT-сессию — второй тип креденшела не вводим.

**Учёт — гранулярность (уточнение контракта):** `/v1/usage` отдаёт агрегаты
(суммарные и маргинальные), не строки запросов и не матрицу день×модель.
Разрез день×модель получаем запросом на конкретный день
(`start_date=D&end_date=D` → `model_stats` этого дня). Запросы всегда с явными
датами. Календарный день — **UTC**, диапазон `[D 00:00Z, D+1 00:00Z)`;
на стенде `TZ=UTC`. `model_stats: []` означает успешный нулевой результат.
Отсутствующее/невалидное поле или ошибка HTTP означает **недоступный учёт**,
а не нулевые расходы. Текущий sub2api скрывает ошибку получения статистики
и опускает поле также при пустом результате: до интеграции нужна небольшая
правка стенда — явный массив при успехе и non-2xx при ошибке (§8, шаг 0).
Успешный HTTP ещё не означает финальность: запись usage у sub2api асинхронна.
Контракт gateway ограничивает задержку записи завершённого запроса 24 часами
и запрещает более поздние изменения уже устоявшегося дня. Эту границу
подтверждаем на шаге 0; без неё интеграция не принимается. Финализация дня
использует также повторное чтение после окна стабилизации (§6.2).

Маппинг денег: `ModelStat.actual_cost` → `billableUsd`, `cost` →
`apiEquivalentUsd`/совместимый `estimatedUsd`, `source: 'gateway'`,
`billingMode: 'api'`. `account_cost` — расход аккаунта бэкенда, не тиммейта.
Токены и `requests` переносятся из соответствующих полей `ModelStat`,
без восстановления стоимости по таблицам цен приложения.
В `normalizeCostBreakdown` явный gateway `billableUsd: 0` сохраняется:
текущее `positive(billableUsd) || estimatedUsd` ошибочно заменяет бесплатное
списание стандартной ценой. Legacy fallback для отсутствующего значения и
поведение остальных источников сохраняются.

## 4. Архитектура

Фича `src/features/gateway-provider/` по `docs/FEATURE_ARCHITECTURE_STANDARD.md`:

```text
src/features/gateway-provider/
  contracts/          # DTO, IPC-каналы
  core/domain/        # GatewayProfile, MemberGatewayBinding, нейтральный connection spec
  core/application/   # use-cases
  main/
    composition/      # createGatewayProviderFeature
    adapters/input/   # IPC
    adapters/output/  # runtime-маппинги, toArtifactId, HTTP-клиент/usage-адаптер
    infrastructure/   # GatewayProviderStore
  preload/
  renderer/
```

| Что                            | Ответственность                                                                                                                                                                              | Где                          |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| `GatewayProfile`               | `id`, `baseUrl`, `displayName`, `allowPrivateNetwork` (default false, привязан к canonical URL)                                                                                              | `core/domain`                |
| `MemberGatewayBinding`         | `(teamName, memberName) → {profileId, apiKeyRef, gatewayUsageRef}`                                                                                                                           | `core/domain`                |
| `resolveGatewayConnectionSpec` | чистая функция → нейтральный spec (`baseUrl`, `profileId`, `credentialRef`, model, `allowPrivateNetwork`); без env-имён, CLI provider-id и `wireApi`                                         | `core/domain`                |
| `toArtifactId`                 | sanitized-префикс + hash исходной пары имён для глобальной записи OpenCode (§5.2)                                                                                                            | `main/adapters/output`       |
| per-runtime маппинги           | spec → env/CLI/config рантайма; существующие швы вызывают эти функции без дублирования форматов                                                                                              | `main/adapters/output`       |
| `GatewayProviderStore`         | один JSON, сериализованный writer: профили, активные биндинги и sources с неизменяемой идентичностью; lifecycle-факты обновляются                                                            | `main/infrastructure`        |
| `GatewayUsageSourcePort`       | порт чтения учёта — в **token-usage** (потребитель импорта), ре-экспорт из `@features/token-usage/main` (deep-import'ы запрещены standard'ом); HTTP-адаптер реализует его в gateway-provider | `src/features/token-usage/…` |

Ключи — в существующем `ApiKeyService` (крипто не дублируем), вне `team.ts`.
Сейчас `save()` создаёт UUID, допускает замену значения по id, а `lookup()`
выбирает по env-имени: стабильность ref и точное чтение по id ещё **не** реализованы.
Добавляем main-only чтение секрета по id. Gateway use-case в
`main/application/` сохраняет/переиспользует ref по fingerprint литерала,
проверяет неизменность значения перед чтением и возвращает литерал + значения
для редакции. Служебное env-имя записи уникально; поиск через общий
`lookupPreferred('CODEX_API_KEY')` для биндинга запрещён. Общую семантику
`ApiKeyService.save()` для остальных клиентов не меняем.

Fingerprint (SHA-256 литерала) хранится только в main-owned store, без литерала;
повторный ввод переиспользует живую запись. Если запись секрета удалена,
повторный ввод того же литерала восстанавливает storage-ref, сохраняя учётную
идентичность. За fingerprint навсегда закреплена пара
`(teamName, memberName)`: использовать ключ у другого тиммейта, в том числе
после отвязки/rename, нельзя. Для нового владельца нужен новый ключ.
Также fingerprint закреплён за первым `canonicalEndpoint`: тот же ключ
на другом endpoint отклоняется **до** пробы `/v1/models`, даже у того же владельца.
Иначе URL-алиасы одного gateway вернут одинаковые дневные суммы под двумя refs.
Удалённая/изменённая через общий редактор запись даёт ошибку чтения ключа;
учётный ref не начинает молча обозначать другой литерал. Такая ошибка —
durable неполнота источника, а не нулевой расход (см. ниже).

`gatewayUsageRef` = SHA-256 кортежа `(canonicalEndpoint, keyFingerprint)`;
повторная привязка/создание профиля с тем же URL не создаёт второй источник.
Запись хранит endpoint, **снимок `allowPrivateNetwork` на момент создания
source**, ссылку на секрет, исторические `teamName`/`memberName`/`agentId`
и первый день учёта. Владелец, endpoint и approval-снимок неизменяемы;
storage-ref можно восстановить только тем же литералом.
Endpoint snapshot нужен, чтобы смена URL профиля не
переписала старые расходы; новый endpoint создаёт новый источник. Записи
источников и владельцев сохраняются после отвязки/удаления профиля.
Чтение historical source не зависит от текущего профиля: main-адаптер берёт
endpoint, approval-флаг и секрет из самого source, поэтому отвязка, удаление
профиля или смена его URL/флага до финализации не отзывают доступ. Профиль
нужен только для нового bind; lifecycle источника ведут §6.1–6.2.

**Правка ключа через общий редактор.** `ApiKeyService.save()` по существующему
id заменяет `encryptedValue`; gateway не считает такую запись «тем же ключом».
Перед каждым чтением main-адаптер сверяет SHA-256 расшифрованного литерала с
fingerprint source. Несовпадение (`credential_changed`) или удаление записи
(`credential_missing`) — ошибка чтения, которая не снимается сама: уже
импортированные суммы и владелец сохраняются, watermark не двигается, источник
помечается **durable неполным** (не нулём) до восстановления прежнего литерала.
Повторный ввод прежнего ключа (fingerprint совпал) снимает неполноту и
догружает дни после watermark; новый литерал на тот же source не пишется —
для него нужен новый bind и новый source (правило fingerprint выше). UI
показывает причину и предлагает вернуть прежний ключ.

**Изменение URL профиля:** пока есть хотя бы один активный биндинг на `profileId`,
изменение нормализованного `baseUrl` отклоняется; `displayName` менять можно.
Проверка и запись выполняются вместе существующим сериализованным writer store,
как и привязка: конкурентные edit/bind не обходят запрет. UI предлагает создать
другой профиль либо сначала отвязать тиммейтов. После отвязки URL можно изменить;
повторная привязка заново вычисляет `gatewayUsageRef` из нового endpoint и ключа
и сохраняет биндинг вместе с новым source в том же JSON; новый endpoint требует
нового ключа по правилу fingerprint выше. Старые sources/runs
не переписываются; работающий процесс сохраняет исходный маршрут. Это обычный
bind-путь, без массового переноса биндингов или миграционного механизма.

При смене endpoint старые процессы продолжают учитывать только свой старый
ключ, новые — только новый: пересечение UTC-дней не удваивает per-key суммы.
Для полного импорта старый endpoint/ключ сохраняют доступными, пока все связанные
процессы не остановлены и `finalUsageDay` не финализирован по §6.1–6.2.
После этого источник больше не опрашивается, endpoint можно отключить.
Если его отключили раньше, известная история сохраняется, остаток явно неполон
до восстановления доступа; смена URL/успех нового ключа не финализирует старый
source. Учёт старого ключа через URL-алиас и перенос его истории в новый source
в эту фичу не входят; приложение не угадывает равенство разных gateway.

Один ключ используется только этим тиммейтом. В диапазоне от первого дня
привязки до `finalUsageDay` учитывается весь ключ, включая обращения вне
приложения. Финализация приостанавливает опрос; UI обозначает источник как
«приостановлен после D». Повторный bind того же ключа догружает **весь** период
после сохранённого watermark, включая внешние обращения за время паузы:
владелец ключа неизменен. Исключения дней без биндинга нет; интервалы привязок
не вводим. Пока source не возобновлён, более позднее внешнее использование
ключа не обещаем показывать как текущий учёт.

Единый resolver секрета потребляют runtime-маппинги, проба моделей,
HTTP-адаптер учёта и редакция артефактов; renderer получает только ref/статус.
Инжект `GatewayUsageSourcePort` → адаптер — в app shell
(`main/index`), без импортов фича→фича. Для frozen-baseline файлов держим
net-дельту ≤ 0; для новых границ фичи включаем eslint-ограничения импорта
(по стандарту).
Порт перечисляет активные и удерживаемые исторические источники с владельцем,
неизменяемым снимком `(canonicalEndpoint, allowPrivateNetwork)` и
lifecycle-фактами (`hasActiveBinding`, `lastBoundAt`, `lastUnboundAt`, `hasRuntimeArtifact`,
`runtimeArtifactRetiredAt`), читает день по
`gatewayUsageRef`; секрет резолвится только внутри main-адаптера.

## 5. Доставка биндинга в рантаймы

Сейчас `buildCrossProviderMemberArgs` собирает один `envPatch` на провайдера,
мержится в общий `shellEnv` — два тиммейта с разными ключами невозможны.
Контракт меняем на per-member: `Map<memberName, {envPatch, configOverrides}>`.

### 5.1 Точки per-member инъекции

Потребители нового контракта (все, кого трогает смена формы результата):

- `TeamProvisioningCreateDeterministicSetupFlow` (~:335 мерж в `shellEnv`) —
  member-патчи больше **не** попадают в общий `shellEnv`;
- `TeamProvisioningLaunchDeterministicSetupFlow` (:412) — то же;
- `TeamProvisioningLaunchDeterministicSpawnFlow` (:111, :587 →
  `inheritedProviderArgs`) и `TeamProvisioningLaunchDeterministicRunFlow` (:84);
- `buildWorkspaceTrustLaunchArgs`
  (`TeamProvisioningWorkspaceTrustLaunchArgs.ts:19`, spread всех полей:38–46);
- type-only правки подписей: `TeamProvisioningEnvRuntimePorts.ts:34–38`,
  `TeamProvisioningProviderRuntimeFacade.ts:147`.

Точки применения per-member env:

- **Прямой путь** (рестарт/добавление): `TeamProvisioningMemberLifecycle`
  уже строит env per-member (:632) и передаёт в `spawnCli` (:986–996) —
  member-патч ложится сюда.
- **Bootstrap-путь** (создание/запуск через лида): передаются и env, и
  per-member Codex overrides/login mode → шаг 3а (§10). In-process lane (`handleSpawnInProcess`) тиммейта в
  процессе лиды per-member env принять не может → **gateway-биндинг требует
  separate-process спавна** (tmux/native); in-process + биндинг = prepare-ошибка.

Биндинги резолвятся в `buildCrossProviderMemberArgs` через lookup-порт по
образцу `TeamProvisioningEnvRuntimePorts` (инжект композицией; `memberSpecs`
из team-конфига ключей не несут). Единая функция применения
`applyGatewayMemberEnvPatch` — финальное применение патча в прямом пути;
оркестратор применяет такой же узкий патч в своей границе спавна. Общий
runtime-пакет между репозиториями ради этого не вводим.

Bootstrap-member передаёт также непрозрачный `gatewayUsageRef`.
`buildTeamBootstrapRequestFingerprint` учитывает его и нормализованные Codex
overrides, иначе смена биндинга может выглядеть повтором старого intent.
Литералы env в fingerprint/диагностику не включаются.

**Порядок применения (constraint):** gateway-патч применяется строго **после**
`applyProviderRuntimeEnv` и **вне** team runtime settings bundle — тогда
`clearExplicitAnthropicRouteEnv` и `stripCompetingAnthropicEnv` его не видят,
правки в них не нужны. Gateway-режим не сочетается с helper-режимом.
В оркестраторе недостаточно обычного `extraEnv`: `buildInheritedEnvObject`
после него снова копирует `process.env.ANTHROPIC_AUTH_TOKEN` лида
(`spawnUtils.ts`, блок после merge `extraEnv`). Gateway-патч применяется
**после всех** inherited-auth преобразований, включая этот блок и
`shouldClearAnthropicApiKeyForTeammateSpawn`. Claude-патч также обнуляет
конкурирующий `ANTHROPIC_API_KEY`. После финального патча общая auth
нормализация повторно не запускается.
Один фронтовый env-тест и свой оркестраторный spawn-тест проверяют явно
разные parent/member tokens и member URL; общих фикстур между репо нет.

### 5.2 Per-runtime артефакты

Маппинг spec → артефакт — чистые main-side адаптеры (§4): core не знает
форматы `ANTHROPIC_*`, Codex CLI и OpenCode JSON. Ниже — что адаптеры собирают:

| Рантайм     | Артефакт тиммейта                                                                                                                                  | Стык (только вызывает маппинг)                                                                                                    | Per-member механизм                                                                                                                                                  |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Claude Code | env `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`, очистка конкурирующего `ANTHROPIC_API_KEY`                                                      | `TeamProvisioningEnvBuilder` (лимит 800, запас есть)                                                                              | финальный member env-патч (§5.1)                                                                                                                                     |
| Codex       | per-process провайдер `agent_teams_custom`, собственный `base_url`, `env_key="CODEX_API_KEY"`, `wire_api="responses"`, `forced_login_method="api"` | существующие builders в `src/main/services/runtime/ProviderConnectionService.ts`; обе формы CLI (`-c` и inline `--settings` JSON) | отдельные настройки и ключ каждого member, включая bootstrap; provider-id совместим с allowlist оркестратора                                                         |
| OpenCode    | запись провайдера в (глобальном) `opencode.json`, `apiKey = {file:~/.config/opencode/agent-teams-credentials/…}`                                   | `OpenCodeLocalProviderConnector`/`OpenCodeLocalProviderSupport`                                                                   | per-member запись + model-route `<providerEntry>/<modelId>`; файл ключа пишет **существующий** writer коннектора (rotation-имена, `assertProviderApiKeyReplacement`) |

**Глобальные OpenCode id:** `gateway-<sanitized-team>-<sanitized-member>-<hash>`.
Hash — первые 12 hex SHA-256 от `JSON.stringify([teamName, memberName, gatewayUsageRef])`,
префикс ограничен по длине, алфавит `[a-z0-9_-]`. Это различает и `a.b`/`a-b`,
и пары `(a-b,c)`/`(a,b-c)`; одного team-scoped префикса недостаточно.
Новый source получает отдельный id: смена биндинга не переписывает запись
живого старого процесса. Перед заменой проверяем владельца и usage-ref; при
несовпадении — ошибка, а не перезапись чужой записи. Вся функция — `toArtifactId`.
Gateway writer не меняет глобальные `model`/`small_model`
(`setAsDefault = setAsSmallModel = false`); model-route передаётся member.
В `configureLocalProvider` передаётся сохранённый `allowPrivateNetwork` профиля;
его штатный путь пишет private-network approval для получившихся config/id/URL.
Это разрешение сохраняется через reload; main не подставляет true без согласия
профиля и не обходит `normalizeRuntimeLocalProviderTarget` прямой записью файла.

**Retirement OpenCode:** после отвязки и завершения последнего app-owned run
этого source удаляем его глобальную provider-запись и managed credential-файл
через тот же сериализованный JSONC writer. Сейчас у connector нет удаления:
добавляется узкий idempotent retire-метод, переиспользующий проверки ownership,
`containsStringReference` и `removeManagedProviderCredential` из support.
Удаляем только запись/файл с совпадающими owner, usage-ref и credential-ref;
чужие изменения и остальные provider-записи сохраняются. Перед удалением
проверяются также ссылки конфигурации на этот provider, включая `model`/
`small_model`: пользовательский маршрут не оставляем висячим. Пока остались
такие ссылки, ссылки на старый credential или очистка не завершилась, `hasRuntimeArtifact = true`
и source продолжает импортироваться. Успешная очистка фиксирует
`runtimeArtifactRetiredAt` в GatewayProviderStore; сбой между удалением файла
и этой записью безопасно повторяется существующим runtime reconciliation.
Cutoff не предшествует retirement (§6.1), поэтому все ещё возможные через
артефакт запросы попадают в период импорта. Нового сборщика файлов/таймера нет.

Codex использует фиксированный `agent_teams_custom` только в аргументах
отдельного процесса, не пишет общий конфиг. Поэтому коллизии между его
тиммейтами нет и расширять `codexNative/customProviderConfigOverrides.ts`
для новых id не требуется; round-trip существующего parser проверяется тестом.

### 5.3 Утечки ключей

Bootstrap-spec env несёт литеральные значения ключей (оркестратор не умеет
резолвить ref'ы) — литерал и список значений для редакции рождает единый
use-case §4 (main/application). Поэтому: ключи **не** попадают в диагностику/
логи (whitelist-only в `TeamProvisioningRuntimeDiagnostics` остаётся
whitelist-only), а в launch-failure артефактах редактируются по **известным
значениям** из того же use-case; паттерны под кастомные форматы не плодим.
Стендовые `sk-...` уже покрыты существующей редакцией.

Временный spec с литералами — **одноразовый**, а не долговременное хранилище.
Пишем его в выделенный app-owned каталог этого профиля (0700), файл — 0600;
маленький ownership-marker содержит launch/process identity, без секретов.
В `teamBootstrapEntry` после единственного чтения и нормализации request
секретный spec удаляется до дальнейшего bootstrap; retry внутри этого процесса
использует request в памяти. Для **межпроцессного auth retry** main хранит
исходный bootstrap-spec только в памяти run до `provisioningComplete`, завершения
единственной разрешённой попытки auth-retry либо cleanup run.
`TeamProvisioningAuthRetryRecovery` после подтверждённой остановки старого
процесса и перед replacement spawn повторно материализует одноразовый spec
тем же writer, обновляет `--team-bootstrap-spec` в сохранённых args и
`run.bootstrapSpecPath`. Восстанавливается исходный intent с теми же member
ключами, overrides и fingerprint, без резолва текущих биндингов и без повторной
отправки уже submitted/unknown первой задачи (существующий guard сохраняется).
Невозможность восстановить spec завершает retry обычным failed-cleanup путём;
при отмене/ошибке spawn новый файл также удаляется. После окончания retry/cleanup
ссылка на in-memory spec освобождается; в diagnostics/snapshot она не попадает.
При ошибке чтения/валидации выполняется та же очистка файла, а штатный
main `finally` остаётся идемпотентным. Удаляются только файлы с подтверждённым
app ownership, не произвольный пользовательский `--bootstrap-spec`.
На старте приложения узкая очистка удаляет оставшиеся файлы завершённых/
аварийных запусков этого профиля; live consumer проверяется через существующее
наблюдение launch-owned процессов и не затрагивается. Symlink/чужие каталоги
не обходятся; daemon или общая очистка temp не нужны. Это закрывает падение
Electron до `finally`; тесты охватывают падение до/после чтения и живой consumer.

## 6. Учёт расходов (token-usage)

### 6.1 Источник и сохранённая идентичность

У каждого gateway-запуска **один источник расходов — gateway**. До спавна
фиксируем `gatewayUsageRef` в main-owned launch/run metadata и
`TokenUsageRunDto`; restart/add/bootstrap фиксируют его одинаково. Discovery
(`TeamLaunchRunSourceDiscovery` и composite merge) и ledger сохраняют marker,
не резолвят его заново по текущему биндингу. Смена биндинга действует со
следующего запуска; уже работающий процесс и его учёт сохраняют свой источник.

CLI-импортёры пропускают такие runs. Attribution policy также исключает уже
сохранённые локальные события marked-runs из расходов, чтобы обновление ledger
или повторный CLI-импорт не создали дубль. У обычных runs поведение прежнее.
Если gateway недоступен, локальные расходы **не** подставляются: сохраняем
последние известные данные и показываем неполноту. Сверки имён моделей,
покрытия бакетов и reconciliation-сервиса не требуется.

Источник учёта (§4) хранит исторического владельца независимо от активного
биндинга. Импортёр берёт `teamName`/`agentName`/`agentId` из этого snapshot;
при upsert владелец существующего события не меняется. Новый endpoint или
ключ создаёт новый источник; прежние события и секрет для незавершённого
импорта не удаляются автоматически. Старый источник дочитывается, пока есть
его активный биндинг, runs или runtime-артефакт (§5.2), затем до стабилизации
последнего дня (§6.2).
При bind `GatewayProviderStore` в той же JSON-записи сохраняет `lastBoundAt`;
при отвязке/замене — `lastUnboundAt` старого источника. Порт возвращает эти lifecycle-факты
и после перезапуска. Ledger выводит `lastUsedAt` как max от времени отвязки,
terminal-времён связанных runs и `runtimeArtifactRetiredAt` (если был артефакт).
Поэтому **отвязка до первого запуска** тоже
имеет cutoff от времени отвязки (с учётом retirement, если артефакт уже был),
без создания фиктивного run. Пока биндинг или
run или runtime-артефакт активен, окончательного cutoff нет. Повторная привязка того же source
снимает финализацию и возобновляет импорт с сохранённого watermark.
Удалённый/отозванный или заменённый через общий редактор ключ означает
неполноту, не потерю уже импортированных сумм. Ошибка fingerprint/чтения
креденшела записывается в durable `sourceStates.degraded` обычным batch-путём,
так что snapshot и бюджеты сохраняют неполноту после перезапуска. Приложение
само не удаляет нужный исторический секрет; сторонняя правка через общий
редактор может лишить доступа к нему. Для дочитывания требуется восстановить
тот же литерал (§4); хранение предыдущих версий секрета не вводим.

Связь source→run и граница использования не зависят от файлов discovery:
ledger сохраняет marked-runs в `replaceRunsForSource`, как уже сохраняет runs,
на которые ссылаются CLI-события. При stop/terminal event/удалении команды
main записывает terminal/last-use сведения **до** удаления launch-файлов;
состояние источника хранит `lastUsedAt` и `finalUsageDay`, закрываемый после
отвязки и завершения последнего связанного run. Polling завершён только когда
`finalUsageDay` прошёл стабилизацию и вошёл в durable watermark (§6.2).
Исчезновение discovery само по себе не считается
доказательством завершения: сохранённая связь остаётся, источник — pending/
degraded до существующей runtime reconciliation. Новый lifecycle-сервис не нужен.

### 6.2 Дневной импорт и DTO

Импортёр в token-usage реализует `TokenUsageImporterPort`, HTTP-адаптер в
gateway-provider реализует `GatewayUsageSourcePort`; композиция — app shell.
Запуск — существующий `refreshSnapshot`, отдельного scheduler нет. Первый
импорт: с UTC-дня первой привязки до сегодня. Следующие: все дни после
watermark (даже уже читавшиеся успешно), вчера и сегодня. Watermark отмечает последний
**непрерывно успешно импортированный и стабилизированный** UTC-день;
не перескакивает через ошибку и не закрывает today. Так перечитываются
все ещё не стабилизированные дни, даже если они старше yesterday.
Учёт до первой привязки не обещаем;
первый день импортируется целиком, без отсечения времени внутри дня.

**Стабилизация:** день допускается к финализации после `endOfUtcDay + 24h`.
Нужно полное успешное чтение **после** этой границы, с upsert всех поздних
записей и нулевых/исчезнувших моделей. Чтение до границы сохраняет события,
но не продвигает watermark; ошибка после границы тоже его не продвигает.
Граница определяется из UTC-дня и фиксированного окна договора §3, поэтому
дополнительные candidate-таблицы/таймеры не нужны. Watermark коммитится вместе
с событиями; restart сохраняет необходимость позднего чтения. Это условие
обычного refresh, без дополнительного scheduler. Успешные
ещё не устоявшиеся суммы видны как данные на момент загрузки; HTTP-ошибка
сохраняет прежние суммы и `degraded`. Остановка процесса или один успешный
ответ сразу после полуночи сами по себе не финализируют источник.

Каждый день читается отдельно: `start_date=D&end_date=D`. Полный валидный
ответ даёт событие на модель. Детерминированный id — hash кортежа
`(gatewayUsageRef, day, model)` с namespace `gateway`, существующий upsert
обновляет растущий today-бакет. Если успешный ответ убрал ранее известную
модель или вернул пустой массив, импортёр возвращает её прежний id с нулевыми
токенами, деньгами и `requestCount: 0`; это обнуляет устаревшую сумму через тот
же upsert. Импортёр читает прежние gateway-события через существующий ledger
port; новый механизм удаления/замены разделов хранилища не нужен.
Ошибка/отсутствующее поле не порождает обнулений и не двигает watermark;
правка/удаление ключа через общий редактор — та же durable неполнота с
причиной `credential_changed`/`credential_missing` (§4), не здоровый ноль.

**Контракт частичного результата:** сейчас `TokenUsageImporterPort` возвращает
только массив событий. Расширяем результат до массива (старые импортёры без
изменений) либо `TokenUsageImportBatch {events, sourceStates}`. Состояние на
источник содержит `gatewayUsageRef`, владельца, непрерывный watermark,
`lastUsedAt`/`finalUsageDay`, `degraded`, `degradedReason`
(`http_unavailable` | `credential_changed` | `credential_missing`) и
`lastSuccessfulAt` последней
полностью успешной загрузки.
Gateway-импортёр возвращает успешные дни вместе с признаком ошибки остальных;
исключение не используется для отбрасывания уже полученных дней.

Единственный владелец checkpoint/status — **token-usage ledger**, а не
`GatewayProviderStore`. `TokenUsageAnalyticsService` под существующей
`SerialQueue` передаёт batch в узкий `commitImportBatch`: события и
`sourceStates` сохраняются одним существующим atomic write. Watermark/успех
не записываются импортёром до этой операции; отказ записи не продвигает их.
`readSnapshot()` возвращает также состояния (у старого ledger — пустой набор),
поэтому refresh, `getSnapshot` и publish вычисляют `degraded` одинаково после
перезапуска. Отсутствующее состояние gateway-источника означает «ещё не загружено».
Чтобы это работало сразу после bind, `getSnapshot`, `getBudgetStatus`, publish
и tick получают актуальный inventory через **тот же** `GatewayUsageSourcePort`
(только локальные metadata, без HTTP). Объединяем inventory с ledger states:
у source без состояния — неполнота с первого чтения, даже если refresh ещё
не запускался. Для повторной привязки действует то же правило, пока нет
успешной загрузки после inventory `lastBoundAt`; старая успешная state-строка
не снимает pending нового bind. Ошибка чтения inventory тоже не становится здоровым нулём.
Состояния/история в ledger сохраняются; отдельный inventory-reader не нужен.
Обычные массивы сохраняются прежним путём. Новых менеджеров/транзакционного
движка или отдельного reader-порта состояния не вводим.

Минимальные расширения существующих DTO и обоих normalizer'ов сохранения:

- Run: `gatewayUsageRef?: string` — snapshot источника при запуске.
- Event: `gatewayUsageRef?: string`, `gatewayDay?: string` (`YYYY-MM-DD`, UTC),
  `requestCount?: number` — конечное неотрицательное целое; отсутствует → `1`
  для старых событий. `requests` не прячем в `providerUsage`: сейчас его тип и
  ledger-normalizer сохраняют только Kiro.
- `requestCount` и все `*RequestCount` billing-счётчики используют один вес;
  `exactEventCount`/`estimatedEventCount` остаются количеством ledger-событий.
  Деньги и токены нормализуются по §3, `usageSourceKind: 'gateway_exact'`.
- `appRunId` остаётся обязательным: `gateway:<gatewayUsageRef>:<day>` — только
  namespace агрегата. Соответствующий фиктивный `TokenUsageRunDto` не создаём.
  `occurredAt = D 00:00Z`. Runtime неизвестен из gateway-агрегата
  (`runtimeKind: 'unknown'`), не угадываем его по последней конфигурации.

### 6.3 Проекция и неполнота

В `keepOnlyMappedUsageEvents` добавляется **узкое** правило до отбрасывания
orphan-событий: валидный `gateway_exact` с `gatewayUsageRef`, `gatewayDay` и
историческим владельцем допускается без реального run. Обычный orphan с одним
`agentName` по-прежнему unmapped. В `snapshotProjection` aggregate-события
входят в общий итог, `byTeam`, `byAgent`, `byModel` (модель из события),
календарные графики и runtime `unknown`. Ключ агента совпадает с существующим
team-scoped ключом. Файл frozen: новую связную политику выносим без роста cap.

До этой политики уже вызывается `filterEvents`: сейчас при team-filter он
также требует реальный run. Для проверенного gateway-агрегата фильтруем по
сохранённому `event.teamName` через существующий `teamIdForName`, без lookup
несуществующего run; `teamIds`/`teamNames` и `agentId` не теряют эти события.
Обычные события сохраняют текущие правила фильтрации.

Агрегаты не увеличивают число реальных runs и не участвуют в `byTask`,
`byProject`, `bySession`, `byCommand`, recent/expensive/session/command runs.
Иначе дневная сумма ложно приписывается одной задаче по времени `00:00`.
Dashboard обозначает гранулярность «по дням UTC»; для gateway range округляется
наружу до целых UTC-дней. Фильтры конкретной сессии/команды агрегат не включают;
временные фильтры обычных событий не меняются.

**Совместимость существующих бюджетов:** второй потребитель
`keepOnlyMappedUsageEvents` — `budgetPolicy.ts`; его `runById.get(...)!` после
допуска агрегатов больше не является инвариантом. Gateway-расходы включаются
в global/team суммы по владельцу события без реального run. Проект не
выдумывается: для проектов, связанных с marked-runs этого источника, обе
budget-метрики помечаются `incomplete`, поскольку дневную сумму нельзя
распределить по проектам. Если для участвующего в текущем месяце gateway-источника
ещё нет состояния либо его импорт неполон/`degraded`, обе метрики global и
соответствующего team также `incomplete`, включая бюджет без уже импортированных
событий. Показывается известная частичная сумма, а не подтверждённый ноль.
Полная успешная загрузка снимает эту неполноту global/team; проектная остаётся
из-за невозможности распределения. Сохраняются существующие запреты уведомлений
по `status.degraded` и `metric.incomplete`; нового evaluator не требуется.
`getBudgetStatus`/publish/tick
читают durable статус источников из ledger, как аналитические snapshot-пути;
после перезапуска нельзя считать данные полными только потому, что
in-memory `refreshDegraded` сбросился.

До первого успешного чтения и при неполных днях snapshot помечается
`degraded`, UI показывает неполноту и время последней успешной загрузки,
а не подтверждённый ноль. Статус читается из того же ledger snapshot, что и
события; `gatewayLastSuccessfulAt` добавляется в snapshot DTO для времени
последней полностью успешной gateway-загрузки (не текущее `updatedAt`). Статус
учитывается также обычным `getSnapshot`/publish после перезапуска; успешный
HTTP без `model_stats` не снимает ошибку. Успешный явный пустой массив — ноль.
Новое поле времени сохраняется также `contracts/normalize.ts`, иначе renderer
потеряет его на границе API. При нескольких источниках показывается самая
ранняя из последних полных загрузок; если хотя бы один ещё не загружался,
время не показывается как общий подтверждённый успех.

## 7. UI

1. **Настройки → «Gateway providers»**: CRUD профилей. Отдельной «проверки
   соединения» нет — она совмещена с пробой ключа (§7.2). URL привязанного
   профиля защищён правилом §4; ошибка сохранения объясняет следующий шаг.
2. **Строка тиммейта** (`MemberGatewaySelector` рядом с `TeamModelSelector`):
   выбор профиля + ввод ключа (сразу в `ApiKeyService`, в UI не отображается) +
   выбор модели из `GET /v1/models` **его ключом** (= проба ключа; невалидный
   ключ → ошибка на строке). Пустой каталог моделей → ошибка на строке
   («каталог моделей пуст»), ручного ввода модели нет.
   `MemberDraftRow` (frozen cap 1001) — врезка компонента, net-дельта ≤ 0.
3. Смена имени команды/тиммейта → биндинги отвязаны; ручная привязка с новым
   ключом, т.к. прежний сохраняет исторического владельца. Смена профиля/ключа
   применяется к следующему запуску; UI не обещает сменить маршрут живому
   процессу. Исторические источники не скрываются из учёта вместе с профилем.

5. **Смена биндинга** → следующий запуск получает новый источник, текущий
   сохраняет старый. Re-import не меняет исторического владельца; передача
   старого ключа другому тиммейту отклоняется, в том числе после rename.

Минимальные автоматические проверки — в существующих suites, без нового
тестового стенда/общего пакета фикстур:

- Gateway binding/store: повторный ввод ключа, конкурентная привязка,
  другой владелец после отвязки, изменение/удаление секрета, коллизии id;
  удалённый HTTP отклоняется, локальный HTTP и удалённый HTTPS допускаются.
  Частный HTTPS проходит OpenCode prepare только с сохранённым разрешением;
  reload его сохраняет, изменение URL сбрасывает; loopback не требует флага.
  Замена/удаление ключа через общий редактор до финального импорта оставляет
  старые суммы и durable неполноту (`credential_changed`/`credential_missing`)
  после reload; восстановление тем же литералом снимает её и догружает дни.
  URL связанного профиля не меняется, включая гонку edit/bind; отвязка →
  новый URL + новый ключ → повторная привязка переживает reload с новым usage-ref.
  Удаление/смена URL или approval-флага профиля после отвязки до финального
  чтения не меняет сохранённый endpoint/approval snapshot: adapter продолжает
  читать источник с прежним разрешением; после финализации источник не
  опрашивается.
  Старый ключ на URL-алиасе отклоняется до auth-пробы; пересекающиеся старый/новый
  runs с разными ключами не дублируют суммы. Отключённый до финального чтения
  старый endpoint сохраняет известные суммы и неполноту, после финального —
  больше не запрашивается и не мешает новому source.
  В существующей prepare/пробе ключа фикстуре URL запроса, `/v1/models` и marker
  следующего запуска относятся к новому source; история остаётся у старого.
  OpenCode: старый artifact живёт до остановки consumer, затем удаляется вместе
  со своим unreferenced ключом; новый source/чужая запись не затронуты. Сбой
  cleanup/restart и пользовательская ссылка `model` сохраняют активность source
  до idempotent retirement; чужие defaults не меняются.
- Env/bootstrap: итоговые разные parent/member tokens, per-member URL и
  Codex overrides, strict schema/fingerprint round-trip, все separate-process
  ветки; очистка одноразового spec при успехе/ошибке и после падения, без
  удаления пользовательских файлов или spec живого consumer. В существующей
  auth-retry suite: первый consumer прочитал и удалил spec → auth failure →
  replacement получает восстановленный исходный spec; тот же fingerprint и
  guard первой задачи, очистка при отмене/ошибке повторного spawn.
- Token-usage importer/ledger/projection: дневной re-import без дублей,
  обнуление исчезнувшей модели, round-trip `requestCount: 0/25`, сумма всех
  request-счётчиков, история владельца, gateway + CLI того же run учитывается
  один раз, gateway без real run виден в общих/team/agent/model итогах;
  обычный orphan остаётся unmapped, дневная сумма не попадает в задачу/сессию.
- Та же gateway-фикстура под team-filter и в существующем budget status:
  сразу после bind и до первого refresh snapshot/бюджет видят неполноту;
  global/team суммы совпадают с аналитикой без падения на отсутствии run,
  затронутый project-budget неполон и не отправляет threshold-уведомление;
  до первого успеха/при частичном импорте global/team также неполны и молчат,
  в том числе после перезапуска, а полный re-import снимает эту неполноту.
- UTC/ошибка: сутки на границе месяца, successful empty против missing/error,
  `actual_cost: 0` при положительном `cost`, сохранённые суммы и `degraded`
  после ошибки и перезапуска; успешные дни сохраняются при частичной ошибке,
  отказ записи batch не продвигает watermark и повтор не дублирует события.
- Источник после удаления discovery/team-файлов: marked-run и last-use cutoff
  остаются в ledger; последний закрытый день дочитывается, неизвестный конец
  не объявляется успешно финализированным. Bind → unbind без spawn сохраняет
  cutoff через reload; повторный bind возобновляет импорт. С существующими fake
  clock/HTTP-фикстурами проверяется и bind после нескольких дней паузы: сразу
  pending, затем все пропущенные UTC-дни включены один раз с прежним владельцем.
  С теми же fake
  clock/HTTP-фикстурами: последний запрос перед полуночью записан с задержкой,
  первая успешная загрузка не финализирует день, повторное чтение после 24h
  включает позднюю запись и завершает импорт; ошибка и restart не теряют её.

Команды реализации: `pnpm exec vitest run <затронутые suites>`,
`pnpm lint:fast:files -- <затронутые файлы>`, `pnpm typecheck`,
`pnpm guard:source-file-size`, `pnpm guard:team-provisioning-architecture`.
Для широкого изменения границ — полный `pnpm lint`; обязательный CI по
политике проекта сохраняется. UI-проверка — `pnpm dev:mcp` через CDP 9222,
fixture/test APIs, без Computer Use/нативного folder picker. Live smoke
использует `cli-source`; перед выпуском отдельно проверяется построенный и

### Crash recovery acceptance clarification (2026-10-21)

- A binding allocated for a member absent from the saved roster carries durable
  ownership of the issuing renderer document. Cancellation, document reload/crash,
  and app restart reclaim only matching provisional receipts. No TTL is used.
- Initial recovery starts in the background after the existing configuration fence
  is wired, without gating startup or ordinary APIs. Service-local live owners
  protect current renderer drafts; exact previous-process or explicit-loss receipts
  recover under that fence with roster writes and team lifecycle operations. Both saved offline `members.meta.json` rosters and native
  `config.json` rosters count as saved membership. Launch snapshots and runtime
  artifacts preserve source ownership/history even without a current live process.
- A never-saved, never-launched draft releases its binding, profile reservation,
  and key fingerprint, including superseded provisional keys. Historical sources,
  shared key-editor records, and committed credential replacements survive.
- Owner scoping and exact receipts protect other windows and later replacements,
  including same-tick rebinds. Missing files differ from unreadable/malformed
  evidence: the latter preserves that team's state and logs a safe warning while
  healthy teams continue, without blocking app initialization. Legacy unmarked records are not guessed to be drafts.
- Focused service/store restart and IPC lifecycle tests verify these boundaries.
  This clarification does not claim a fresh live-runtime E2E pass.
